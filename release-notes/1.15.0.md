# TPS Global Context Menu 1.15.0

## Intent

Give TPS consumers one canonical binary task-completion operation instead of requiring each plugin to guess checkbox markers or omit GCM's note-level completion follow-up.

## Changes

- Adds `plugin.api.tasks.setCompletion(ref, completed)` to the existing version-1 Task API.
- Maps `true` through the configured `complete` status and `false` through `todo`, including custom checkbox markers, only when the task is not already semantically at the requested target.
- Reuses the guarded atomic Task API update path, invokes GCM's recurrence, final-note-status, and checklist-property follow-up, then resolves the current task from authoritative post-follow-up content before normal invalidation.
- Classifies configured task markers consistently across Task API records, final-note prompts, and checklist-open properties. Custom Todo/Working markers remain open, Complete/Won't Do are terminal, and migrated scratchpad records remain outside both groups.
- Preserves custom Working, Won't Do, and migrated markers on same-value calls. Removed, replaced, or post-follow-up ambiguous rows yield `task: null` rather than trusting a stale absolute line.
- Reads current content after recurrence before deciding that a note has no open tasks, guarantees status-choice dismissal settles exactly once, attempts independent follow-up stages even after an earlier failure, and reports `ok: false, changed: true` when the checkbox write committed but follow-up was incomplete.
- Leaves `tasks.setCheckbox(ref, checkbox)` unchanged as the raw-state compatibility method.

## Compatibility and migration

- Backward-compatible minor release; no settings or note-data migration.
- Minimum supported Obsidian version remains 1.10.0.
- Consumers should feature-detect `tasks.setCompletion`; older Task API v1 objects remain valid but do not provide canonical binary completion.

## Validation

- Thirty focused Task API/menu/follow-up/modal checks verify custom complete/todo mappings, Working, Won't Do, migrated state, effective returned status, completed-date behavior, exact post-recurrence rereads, removed-line fail-closed behavior, recurrence ordering, failure isolation, prompt dismissal, and raw `setCheckbox` compatibility.
- Eighty-four related task/status/Base/recurrence/contract checks, TypeScript, the complete declared suite, final build, and test-vault reload pass for the released artifact. Live smoke covered the configured mapped task menu plus a public API-event completion/reopen round-trip; the synthetic note was moved from `Inbox` to `_archive` afterward.

## Known limitations

- `setCompletion` is intentionally binary. Callers that need a specific nonbinary workflow state should continue using `setStatus` or the raw `setCheckbox` method and own any corresponding follow-up semantics.
- A successful write can return `task: null` when synchronous follow-up removes the row or leaves multiple indistinguishable candidates. Consumers should treat `changed` as the mutation result and the task record as optional.
