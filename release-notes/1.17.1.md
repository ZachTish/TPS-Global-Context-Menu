# TPS Global Context Menu 1.17.1

## Intent

Make checkbox state and task workflow status one deterministic, fail-closed contract across supported TPS surfaces. Structural Markdown tasks remain discoverable even when their marker is not mapped, but unsupported or stale workflow mutations never guess a status, marker, or completion state.

## Changes

- Added one ordered mapping parser/resolver for settings, linked subitems, manual and AI task creation, task menus, recurrence, timers, reconciliation, completed-task hiding, TPS Table/List, Task API mutations, and the public `taskCheckboxes` capability. Runtime consumers receive only the rows actually saved; an empty or partial mapping is no longer silently supplemented with todo/complete defaults.
- The settings editor now validates a local draft and saves only through **Apply mappings**. Invalid, blank, duplicate, multi-character, or unresolved rows cannot replace the last valid runtime configuration.
- Valid aliases and alternate markers remain supported. Saved row order explicitly selects the primary status-to-marker mapping, while the first status in each row selects its canonical reverse mapping.
- Any valid one-character Markdown checkbox remains a structural task, including an unmapped custom marker. TPS Table/List can still query its Kind, title, tags, raw checkbox state, relational properties, and custom formulas, and status grouping places it under **Ungrouped**. It receives no invented workflow status/open/done aliases and cannot be changed through a status-driven control until mapped.
- Unknown statuses and markers fail closed instead of falling back to todo/open. Filter-driven Table/List task creation without an explicit workflow status uses the first configured status that is authoritatively open; explicit todo/complete requests still require those exact mapped statuses.
- Base picker, quick editor/toggle, multi-select, context and native checkbox menus, Task API create/update, recurrence, timers, linked items, and task drops snapshot mapping, ownership, and completion semantics and then revalidate them at the atomic write boundary. A concurrent mapping change causes no note write.
- Checkbox mutations clear the configured workflow field and legacy checkbox-owned `status`, `taskStatus`, `task.status`, `task.checkboxStatus`, and `checkboxStatus` carriers while preserving the exact relational Status property, nested values, protected inline code, unrelated fields, and block IDs. The checkbox marker remains the sole persisted line-level workflow carrier.
- Linked parent/child mutations use authoritative post-write reads. Verified writes survive idempotent results and post-write exceptions; verified divergence is compensated where ownership is still provable, while an unverifiable side is never guessed. Checklist promotion creates one fully seeded, exclusively owned child and removes it only when an authoritative reread proves the parent did not commit.
- New-child and scheduled-note body links resolve the child’s configured workflow key/value through the same ordered mapping. Statusless children keep ordinary bullet links; nonempty unmapped or ambiguous statuses skip link insertion rather than receiving a fabricated `[ ]`, and the resolution is rechecked at the parent-body write boundary.
- Completion classification, icons, uppercase `[X]` normalization, alternate-marker preservation, and editable/reading-mode hiding now derive from configured mappings. Explicitly empty completion/active-status settings remain empty. Reconciliation excludes protected Markdown blocks.
- The public capability reuses one normalized snapshot until the settings array changes, avoiding repeated normalization during Calendar and Kanban row scans.

## Compatibility and migration

- Backward-compatible patch for valid configured mappings; the persisted mapping schema, commands, supported API versions, valid custom markers, notes, and task lines require no manual migration. Legacy rows are canonicalized non-destructively into the existing schema on load.
- Previously accepted multi-character or duplicate-marker rows are rejected because Obsidian checkbox syntax and cross-surface precedence cannot interpret them reliably.
- Unsupported writes that previously guessed a todo/open status or accepted an unowned marker now fail visibly and leave content unchanged.
- Minimum supported Obsidian remains 1.10.0.
- TPS Calendar Base 0.4.3 and TPS Kanban 0.2.2 consume this exact capability and intentionally block status-driven writes when it is missing, incompatible, malformed, or unmapped.

## Validation

- Focused regressions cover parsing, aliases, alternate-marker precedence, explicit Apply behavior, structural unmapped tasks and formulas, canonical workflow-carrier cleanup, manual/AI creation, Task API and menu mutation races, linked-subitem compensation, strict new-child/scheduled-link resolution, checklist-promotion ownership, recurrence and timer creation, protected-block reconciliation, custom completed-marker hiding, Base/List creation and drops, and exact consumer contracts, including deterministic zero-write failures.
- The complete declared GCM suite, TypeScript, mandatory separate production-mode build, and reloaded test-vault UI verification are recorded before publication.
- Test runtime state is preserved. Production is not accessed.

## Known limitations

- Checkbox markers remain limited to Obsidian's one-character task syntax (or the single blank open marker).
- A status absent from the configured mapping table is intentionally not writable through status-driven task operations.
- The explicitly configured linked-subitem open fallback is used only for a statusless linked note; it never substitutes for a nonempty unknown status.
- Parent-line and child-note promotion cannot be one filesystem transaction. GCM therefore uses exact ownership checks, authoritative rereads, and conservative compensation; if either side cannot be proven, it reports the failure instead of deleting or rewriting uncertain content.
