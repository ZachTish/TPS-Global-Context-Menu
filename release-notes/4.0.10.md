# TPS Global Context Menu 4.0.10 — Keep Daily Note lookup warm during unrelated imports

Daily Note lookup now retains its candidate index when a changed Markdown file was and remains unrelated to Daily Notes. This matters when a transaction import has finished writing notes but Obsidian continues delivering metadata events: Navigator's calendar may query GCM for dates, and each ordinary edit previously caused GCM to enumerate and classify every Markdown file again. Obsidian also emits a global `resolved` event after individual edits; repeat events now preserve the warm index after their changed paths have been checked.

Daily Note identity additions, removals, conflicting dates, renames, deletes, configuration changes, initial metadata resolution, and observed full metadata rebuilds still invalidate the index as needed. Pending current-source reads continue to block identity queries until the latest bytes are inspected. There is no note rewrite, repair pass, new watcher, setting, API change, or data migration.

This is a backward-compatible **patch**. Minimum Obsidian remains **1.10.0**. Tested in **Obsidian Plugin Test Vault** and ready for the user's BRAT pull; production has not been modified.

## Validation

- Regressions replay 20 transaction creates and 20 modifies with Obsidian's `changed → resolve → resolved` sequence. The warmed index stays at one Markdown enumeration, with one current-source read per changed file. Tests also cover a full metadata rebuild, Daily Note identity transitions and conflicts, rename/delete, configuration changes, and pending readiness.
- Focused suites pass: 67 Daily Note creation and 41 identity reconciliation tests. The declared versioned test workflow passes 620 pretest and 814 main-stage checks, scheduled-format and time-tracking checks, and its build. The 206 supplemental checks and TypeScript also pass.
- Before the fix, three foreground edits to an unrelated synthetic transaction each caused the next lookup to enumerate the test vault and took **159, 150, and 151 ms**. With the changed plugin loaded, one cold lookup took **193 ms** and enumerated once; the next three transaction edits led to **zero** full scans in each lookup and **0–0.5 ms** lookup time. One other Markdown enumeration occurred outside those lookup windows; its owner was not attributed. The synthetic note's final bytes matched the three intended edits.
- The complete consumer suite remained enabled. The final 4.0.10 plugin runtime was built and the named plugin was reloaded. One further transaction edit after that versioned reload produced **zero** lookup scans, a **0.2 ms** lookup, and exactly the intended note-body change. Its `data.json` SHA-256 remained `a010fa519922568886b6eedfe49aa10371bb9a525d8bd9a312fbfa53b3e249` across deployment. All 12 synthetic QA notes were moved directly to `_archive`, with their bytes checked after the move.
- A cold lookup, real Daily Note change, or full metadata rebuild may still enumerate the vault. These test-vault operation counts are not a production or physical-iPhone speed measurement.
