# TPS Global Context Menu 3.6.12

New task notes finish their initial native-record preparation before GCM makes their title/body editable. Previously native Base creation could present an empty task, then a metadata listener wrote its identity/title and moved it to the native task folder underneath the editor. The existing created-note handoff now awaits that work after initial template/filter writes and before preview, open, explicit destination or stay completes.

This patch removes metadata-triggered adoption, create-triggered draft reads and the 10-second eligibility timer. Create/metadata listeners retain indexing. One explicit handoff consumes eligibility, concurrent preparation shares the existing promise, and preparation errors are logged/reported without automatic retries or caller fallback creation/opening. Ordinary existing-note navigation remains read-only. No new setting, public API version, cache, watcher or repair layer is introduced. Minimum Obsidian: **1.10.0**.

The native envelope, canonical task path, original kind eligibility, exclusions and current-source guards are unchanged. Old files, body-bearing drafts, templates and already prepared native records are not adopted. Routes that do not call the explicit created-note handoff no longer trigger background adoption. A Base explicitly restricted to another folder can still lose the task when the configured canonical folder is elsewhere; this separate location policy and nested-tag mapping behavior are unchanged.

## Validation

- Focused native-record, creation routing and template-protection checks: **141 passed**. Final versioned declared suite: **1,325 passed**; supplemental suite: **197 passed**. Zero failures/skips. TypeScript and separate production-mode build passed with Node 24.19.0/npm 10.9.2.
- A burst of 1,000 post-layout creates plus 3,000 metadata events performs **zero draft cached/raw reads, process attempts, renames or timers**. The explicit handoff performs one preparation/write/rename, repeated/concurrent calls do not duplicate it, and concurrent body edits/new exclusions are preserved. Read/write/rename failures propagate once without metadata retries.
- Final build deployed only changed main/manifest into **Obsidian Plugin Test Vault**. Named GCM disable/loadManifest/enable verified 3.6.12. Relevant consumers stayed enabled. The left Navigator sidebar was collapsed for usable Base geometry and restored afterward; outbound automation remained disabled.
- Actual foreground Base New gestures: ordinary selected-title readiness **49.3 / 38.2 ms**; embedded first-use/standalone repeated native task **126.3 / 72.7 ms**. The first task created its native folders. Every preview had its title selected. No recorded long tasks or note mutations outside the fixture scope occurred in these creation captures.
- Previously the task title was editable at **43.2 ms**, but its separate adoption completed at **103.7 ms**. Now the first task's preparation completes at **104.1 ms**, preview begins afterward, and its final canonical path is already correct when the title becomes editable. The repeated task preparation completes at **53.0 ms**. There are no later preparation writes or renames after preview readiness. This is a correctness/ordering fix, not a claim that the complete task is prepared faster.
- Each task used one core initial-property process plus one native preparation process and one canonical rename, all before presentation. Each ordinary note used one core process and no native mutation. Draft inspection is invoked once per handoff rather than twice by separate events. Ordinary repeated-flow observed reads fell from three cached/three raw calls to two/two; these are inclusive instrumentation counts, not independent disk operations.
- Actual title Enter → editable body readiness: ordinary **75.0 ms**, native task **25.7 ms**. Ordinary filename/title matched; native identity/path stayed stable; both immediately edited bodies were preserved once. This sample had a clean body at title commit; overlapping unsaved body/title interaction is not covered by these timings.
- Six plugin settings remained unchanged in memory/on disk. Runtime data.json and other captured runtime-owned files were preserved; GCM's own recurrence-session file changed during its reload lifecycle and was not overwritten/restored. Hooks were removed, prior leaf/sidebar state restored, and all eight fixture files archived directly to `_archive`. Core Base save was explicitly awaited before detaching/archiving; no cleanup save error occurred.

These small desktop test-vault samples use trusted UI input and two animation-frame observations of visible title readiness, not compositor timing. They do not establish production/iPhone speed or plugin-free performance parity. First process startup, other creation routes and wider interaction coverage remain separate work.
