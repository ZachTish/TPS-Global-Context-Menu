# TPS Global Context Menu 1.33.0

TPS Global Context Menu `1.33.0` makes TPS List and TPS Table filtering deterministic and fixes the production settings bridge that hid synthesized tasks from mixed task/project queries.

## Query correctness

- TPS List receives the real plugin's live checkbox mappings, property definitions, and services through a typed host; List-only defaults no longer masquerade as GCM settings.
- Both custom views compile whole-Base and active-view filters into the same validated plan and evaluate synthesized rows with the same typed filter engine.
- Nested Boolean groups retain their exact meaning. Unsupported or ambiguous clauses fail closed with zero rows and a visible clause-level diagnostic; GCM-owned creation refuses the same invalid query before writing.
- `kind == task OR kind == project` includes mapped task rows plus authored project records. The active view's archive and terminal-status exclusions apply to both. Migrated tasks follow the literal authored filter; use `task.open` for strict open-only behavior.
- `itemKind`, `note.kind`, and `task.status` provide explicit structural, note-frontmatter, and checkbox-workflow namespaces.

## Incremental indexing and progressive results

- A plugin-level row index parses each Markdown file once per revision and is shared by TPS List and TPS Table.
- Cold reads are bounded to eight concurrent files; source lifecycle events invalidate only the affected file; unchanged filter/view rerenders perform no source reads.
- Large scans publish deterministic canonical-path batches with an explicit incomplete indicator and cancellation generation. Stable row IDs preserve selection and scroll anchors while batches arrive.
- Final ordering always uses path, line, entity kind, and stable identity tie-breakers across both custom views. The native bare `folder` alias resolves from the source file path, so archive exclusions do not rely on frontmatter. Compiled plans use a bounded cache keyed by filters, active view, and configured property schema.
- The executable benchmark covers 10,000 files and 100,000 rows, including concurrency, warm-cache, one-file invalidation, deterministic order, progressive batches, and cancellation.

## Compatibility and known limitations

- Backward-compatible minor release with no persisted Base, setting, note, or public API migration.
- Native Obsidian Table/List behavior is unchanged; strict validation and progressive indexing apply to the GCM-owned TPS List and TPS Table views.
- The first cold custom-view load must index candidate Markdown sources. It is bounded and visibly incomplete until the final batch; later unchanged renders are cache-backed.
- Native or hand-edited Base queries cannot be intercepted before save. Unsupported queries therefore render no custom-view rows and identify the invalid clause; no stale or partial result set is presented as valid.
- Minimum supported Obsidian version remains `1.10.0`.
