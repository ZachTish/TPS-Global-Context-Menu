# TPS Global Context Menu 1.30.0

TPS Global Context Menu `1.30.0` replaces the Advanced Canvas property bridge with one GCM-native property system for Canvas, Base, PDF, media, and every other non-Markdown vault file. Source-file bytes remain untouched; ordinary Markdown companions make the properties available to Obsidian Properties, Bases, GCM menus, and TPS integrations.

## Native non-Markdown properties

- GCM lazily creates one Markdown companion under `_assets/TPS File Properties/<source path>.md`; unsafe, overlong, or occupied mirrored paths use `_assets/TPS File Properties/_by-id/<file ID>.md` without overwriting a collision.
- Reserved identity and lifecycle keys are `tpsGcmFileProperties`, `tpsGcmFileId`, `tpsGcmSource`, `tpsGcmSourcePath`, `tpsGcmSourceExtension`, `tpsGcmSourceMissing`, `tpsGcmTombstonedAt`, `tpsGcmPendingTargetPath`, `tpsGcmNeedsMerge`, and `tpsGcmImportedCanvasAt`. All other frontmatter remains directly editable user property data.
- GCM property rows, badges, menus, bulk edits, Vault Query, Notebook Navigator rules, and non-Markdown parent/child relationships resolve the logical source through this common store. The configured exact key/value parent-child ignore rule applies to asset properties too.
- The whole managed companion root is reserved. Files inside it cannot become property sources, and recognized companions are excluded from ordinary note/task/recurrence/relationship/background workflows even if a user moves them elsewhere.

## Bases and TPS List

- A native Base can expose active asset records by requiring `tpsGcmFileProperties == 1`, excluding `tpsGcmSourceMissing == true`, excluding nonempty `tpsGcmTombstonedAt`, and showing `tpsGcmSource` prominently.
- Native Base `file.*` values and the filename column still describe the Markdown companion. GCM's TPS List maps companion rows back to the logical source for file metadata, opening, selection, context menus, sorting, grouping, and editing.
- When a Base result includes both a source and its companion, TPS List deduplicates them in favor of the companion's property values while preserving the configured logical order. The active-record filter intentionally hides missing and tombstoned history rows.

## Identity, lifecycle, and migration

- Stable file IDs and source metadata follow non-Markdown file and folder renames. Companion moves are best effort after the authoritative mapping update, so path collisions do not invalidate an otherwise usable identity.
- Deleting a source removes the live `tpsGcmSource` link and retains its companion as `tpsGcmSourceMissing: true`. A replacement at that path cannot inherit or mutate the retained data implicitly.
- **Relink** deliberately attaches one unique retained companion to a live non-Markdown file. For an exact-path replacement, **Start fresh** tombstones the retained record and creates a separate file ID. Ambiguous identities and collisions fail closed.
- A non-Markdown-to-Markdown type transition is retained with `tpsGcmPendingTargetPath` and `tpsGcmNeedsMerge`; values are not silently injected into the Markdown target. The relink flow diagnoses the pending target, but merging into Markdown requires a future explicit merge action.
- Legacy Canvas `metadata.frontmatter` is copy-only input. The explicit import command or first GCM mutation can copy it into the companion and set `tpsGcmImportedCanvasAt`; Canvas JSON is never cleaned up or synchronized back.

## Public integration contract

- `api.fileProperties` v1 supplies cached/authoritative reads, guarded single and bulk mutation, companion lookup/creation, relink, reconciliation, and known-property discovery. `api.canvasProperties` remains as a deprecated compatibility alias backed by the generic store.
- Public mutations without a valid cause default to automation provenance from the `plugin-api` surface. Callers may declare `user` or `automation` plus a bounded source plugin and surface; GCM-owned direct actions use user provenance.
- Every committed change emits general file invalidation and `tps:gcm-file-properties-updated` with source/property-file paths, stable item ID, action, changed key names, timestamp, source plugin, and optional surface. Property values are never included. Only user causes also emit the explicit-action signal.

## Compatibility and data effects

- This is a backward-compatible minor release. No bulk companion creation or source-file rewrite runs at startup, and the prior Canvas-only API remains available as a compatibility alias.
- Existing legacy Canvas values are preserved in Canvas JSON after copying. Existing Markdown notes and task item-history records are not migrated.
- Minimum supported Obsidian version remains `1.10.0`.

## Known limitations

- In a native Base, `file.*` and the filename column describe the Markdown companion. Use `tpsGcmSource` for the asset link or use GCM's TPS List for logical-source projection.
- A non-Markdown-to-Markdown type transition requires a future explicit merge workflow; this release records and surfaces the pending state but does not merge automatically.
- Item History v1 remains task-only. Asset-property history is planned as a future v2 surface keyed by `tpsGcmFileId`.
- TPS Notebook Navigator's GCM rule automation can use companion properties, but Navigator's own rows, search, and property tree do not yet project them.
- The documented native Base recipe intentionally exposes active companions only; missing and tombstoned records remain stored but are filtered from that catalog.
