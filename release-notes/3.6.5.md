# TPS Global Context Menu 3.6.5

Ordinary note edits no longer reannounce the entire unchanged GCM API merely because Daily Note identity refresh finished. This backward-compatible performance patch removes the mutation-time trigger that caused unrelated Navigator and Calendar work, and removes a duplicate unguarded time-tracking startup scan. Minimum Obsidian remains **1.10.0**.

Daily Note identity still refreshes from current source and rejects stale or ambiguous identity. If an API consumer encounters blocked identity, completion publishes one recovery announcement. Initial load, explicit API requests, saved configuration changes and unload retain their lifecycle announcements. Time tracking retains its existing guarded startup synchronization as the sole timer-discovery owner. Disabled tracking no longer launches a separate scan of all note bodies, while enabled tracking still discovers stored sessions. No settings, defaults, API versions, migration, new cache, watcher, retry or repair behavior.

## Validation

- A regression failed on 3.6.4 before the one-trigger removal. It requires zero readiness announcements for settled create/modify/rename and 20 unobserved body edits, with one existing source-read owner for the burst. It also proves changed identity remains observable despite stale metadata, and a blocked consumer receives exactly one recovery notification.
- Existing cold startup, incomplete metadata, malformed unrelated notes, failed source reads, duplicate callbacks, hot reload and rebuild tests are retained. Explicit API lifecycle and settings-save contract checks remain covered.
- Installed 3.6.4 baseline: six body edits each published the API once despite zero blocked identity queries. Each edit incurred approximately 20,806 native-record inspections and 43,978 metadata lookups across enabled consumers. These are operation counts from the test vault, not production timing or attribution of every lookup to one listener.
- Timer-startup regressions cover disabled startup and disabling before the callback (zero enumeration/body reads), enabling before the callback (one discovery/refresh owner), and restoration of a stored active note timer without writing its target. The installed 3.6.4 facade baseline read 1,000 ordinary note bodies with tracking disabled and refreshed the timer cache twice with tracking enabled.
- The final versioned declared suite passed **1,269/1,269** checks; the supplemental suite passed **187/187**, with zero failures/skips. TypeScript and the suite build passed with `TPS_NO_DEPLOY=1`.
- TypeScript and the mandatory separate final build passed. The normal stable build deployed only to **Obsidian Plugin Test Vault**; an explicit disable, manifest load and enable of `tps-global-context-menu` verified installed **3.6.5**. The final documented build must remain byte-identical to the installed tested artifacts.
- Installed after-comparison: all six ordinary body edits emitted **zero API announcements**, with zero blocked identity queries and body preservation. Four settled samples made **10,413–10,414 native-record inspections** and **22,071–22,072 metadata lookups**, roughly half the baseline. The first post-reload sample remained noisy (20,783 inspections), and remaining consumer scans are not eliminated. These are operation counts, not a controlled end-to-end latency claim.
- The installed compiled timer lifecycle with a synthetic 1,000-note app performed **zero vault enumerations, body reads and cache refreshes when disabled**. When enabled, it retained one enumeration, 1,000 body reads and one refresh. This validates the startup owner without changing actual timer settings or reading/writing fixture notes.
- All **12 real Edit Title UI saves** selected the existing text, preserved body content and left title/filename matching, with one `vault.modify` and one `vault.rename` per save, zero API announcements and no captured long tasks. Median save time was about **138 ms** and visible completion **150 ms**; this descriptive test-vault sample is not a controlled before/after speed claim. Settings and the original leaf were restored.
- Real no-template Daily Note API checks passed cold creation, repeat lookup and concurrent creation: repeated/concurrent calls returned the same file, and concurrent creation created exactly one file. An explicit body edit immediately after creation survived delayed settlement. The temporary in-memory Core Daily Notes options and GCM snapshot were restored, and all five checked persisted settings files stayed byte-identical. This exercises API creation, not every UI entry point, startup cold-cache behavior or an edit during template evaluation.

Tested in the test vault and ready for the user's BRAT pull after publication. No production access or outbound automation. Physical iPhone, complete reminder/calendar latency and native-performance parity are not inferred from this scoped regression. Existing consumer work remains a separate profiling target. No production installation is claimed.
