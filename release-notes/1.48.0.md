# TPS Global Context Menu 1.48.0

GCM now exposes a guarded native-record identity replacement boundary for migrations that need to keep the same Markdown note while changing its stable TPS ID.

- Public `nativeRecords` API version 5 adds authoritative `list(kind?)` and revision-bound `snapshot(kind?)`, exact `planIdentityChanges(...)` path/payload previews, one locked `applyIdentityChanges(...)` batch, plus `canReidentify(reference, nextId)` and `reidentify(reference, nextId, cause)`.
- Re-identification preserves the note path, Markdown body, unrelated frontmatter, ordinary tags, kind, and business fields. It replaces current property identity or a recognized legacy identity tag with the configured property identity.
- The source identity is revalidated inside the source-preserving write. Destination ownership is checked case-insensitively across every native-record kind, including blocked identity evidence, and in-flight creates/re-identifications reserve the destination.
- Missing, ambiguous, malformed, unreadable, duplicate, blocked, occupied, stale, or concurrently changed records fail closed. Malformed property/tag evidence is reserved conservatively across block, flow, indented, sequence, and explicit-key YAML forms. Exact create properties and ordered identity-first updates use the same storage-collision and source-layout guards as the eventual writers.
- Path planning allocates creates and renames as one ordered virtual batch, including suffix collisions and earlier-vacated paths. Apply drains earlier native writes, holds GCM's native mutation barrier, and revalidates snapshot revision, identities, exact payloads, and paths before writing. Storage-profile migration and native draft adoption use the same barrier.
- A truly external Markdown or Sync change between separate file commits can interrupt the batch. The structured result reports aligned committed handles and the failed index so the caller can rebuild authoritative state and retry; deterministic validation and unrelated GCM mutations are rejected before the planned batch starts.

This is an additive API feature. It performs no automatic note rewrite and changes no setting, native schema version, path, command, or body format. Minimum supported Obsidian remains 1.10.0. TPS Controller 0.12.0 is the first consumer.

Known limitation: separate Markdown files are not one database-style transaction. External file or Sync changes during apply can produce a reported committed prefix; callers must rebuild from an authoritative snapshot and retry reconciliation.
