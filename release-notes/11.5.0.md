# TPS GCM 11.5.0 — Broad kinds with subtype tags

Records can use a broad Kind together with a subtype tag, for example `kind: [transaction]` and `tags: [food-entry]`. In Properties → Records, “Identify subtype by” offers Kind only, Tag, or Property. Tag mode shows only the subtype tag; property mode retains the existing key/value controls. Existing mappings remain valid and no vault migration runs automatically.

The shared classifier and native-record creation/update boundary recognize exact, case-insensitive tag membership, preserve unrelated tags, and reject ambiguous subtype combinations. Existing property-to-tag migration can append the marker and remove the old subtype field. Exact paired Base predicates can be converted to tag membership; dependent custom-property scopes, rules, Navigator references, and tag-origin Base edits that need a semantic review block automatic migration instead of rewriting them as scalar properties. Imports and other external readers/writers must be checked before removing their old fields.

No new setting schema, watcher, cache, background pass, or post-create repair was added. The five settings destinations, default destination, disclosure structure, and existing mobile layout are unchanged. The new selector restores focus and participates in native settings search.

Validation: 2,018 test executions passed, no failures or skips; separate final build passed. Focused coverage includes classifier ambiguity, create/update, forward/reverse migration, dependent-reference guards, and conditional controls without settings saves. The final artifacts were deployed and reloaded in Obsidian Plugin Test Vault with Sync disabled. All five settings destinations and all three subtype modes were inspected. A native-created synthetic food log retained its body and unrelated tags, saved quantity 3, and wrote no scalar subtype field. A native Base filtered by broad Kind and subtype tag displayed that record and quantity. Five hundred paired classifier checks caused zero vault scans, body reads, or writes; this is an operation-count check, not a UI latency claim.

Temporary in-memory QA mappings were restored and synthetic fixtures archived. Eight other captured settings/private-state hashes and all enabled states were unchanged. GCM's own data.json hash changed during reload, before the synthetic QA mapping was applied; its startup/persistence implementation is unchanged from 11.4.0. Only a pre-reload hash was captured, so a byte-for-byte preservation claim for that file is not made. No QA mapping was saved, and the disk file remained unchanged throughout the consumer/UI checks and cleanup.

Minimum Obsidian: 1.10.0; Bases requires a host version supporting Bases. Tested in the test vault and ready for a BRAT pull. No production note migration or physical iPhone acceptance is claimed.
