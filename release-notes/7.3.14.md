## Change and boundaries

The existing source verification pass shares an elapsed 8 ms work budget and
one pending real-task continuation across its existing eight read workers.
Checkpointed retained-cache pruning, acquisition, parsing and index commits
give other tasks a turn during genuinely long work. Cheap cache-hit passes
below the budget have no count-only forced yields. The existing startup task
helper and single-flight refresh owner are reused; no persistent cache/index,
additional scan, watcher, poller, repair or retry is added.

Before and after a continuation, both source generation and source revision
must still match. Each queued entry retains its captured path and exact current
file owner. Disposal, modification, rename, deletion, replacement or settings
changes cannot admit stale queued bytes or publish incomplete authority.
Interrupted passes retain dirty paths. All started reads drain before the
owner releases on failure, preserving the original scheduler error rather than
wrapping it as a storage error. A late read after failure cannot schedule an
extra task. Duplicate/conflicting identity ownership still fails closed.

Metadata-only events previously could overwrite an already committed source
entry without changing the source generation/revision. While the existing
authoritative refresh owner is active, those events now leave source projection
to that owner and retain the existing dirty-path signal. No bytes are evicted
and no new generation is fabricated for metadata-only changes. After a failed
owner releases, ordinary provisional metadata handling resumes; subsequent
source reconciliation restores source authority through the retained cache.

The 8 ms checkpoint is not preemption of one expensive operation. The Vault's
inventory call, public snapshot sorting/diagnostics/materialization and other
owners remain separate synchronous costs. Source safety uses the existing Vault
event contract. Tests cover replacement of a queued path without an event, not
global detection of eventless changes to an already committed path. Public API
versions, stored settings, commands, note schema and minimum Obsidian 1.10.0
remain unchanged. Physical mobile/Windows, Reading, foreground input-to-paint
and whole-process cold startup are not certified by these test hosts.

## Serialized synthetic real-task evidence

The published baseline and this source candidate execute the actual service
and existing modeled file/YAML/event harness serially, with a real-task
scheduler and heartbeat. Compilation and setup are outside the measured
verification phase. No CPU cost is injected into these measured runs, no
provider is requested and no actual vault or UI is operated. Complete indexes,
source input bytes and operation counts are preserved.

| Initial authoritative refresh | Baseline | Candidate |
| --- | ---: | ---: |
| 10,000 notes / 2,000 native: longest heartbeat gap | 176.590 ms | 9.280 ms |
| Same fixture: helper tasks / heartbeat ticks | 0 / 0 | 22 / 22 |
| Same fixture: total verification | 175.331 ms | 182.326 ms |
| 10,000 native: longest heartbeat gap | 350.087 ms | 16.236 ms |
| Same fixture: helper tasks / heartbeat ticks | 0 / 0 | 44 / 43 |
| Same fixture: total verification | 348.835 ms | 366.599 ms |

Maximum observed checkpoint slices are 8.275/8.152 ms respectively. Both
10,000-file runs retain exactly 10,000 reads, parses and index operations.
Cheap warm one-edit verification keeps one source read/one index update/9,999
cache hits and zero helper tasks; its measured total is 4.720/7.727 ms for the
2,000-native fixture and 4.592/7.305 ms for all-native. Separate public index
materialization remains synchronous (about 15 ms on the largest fixture).
These are responsiveness/cooperation results, not reduced total CPU work,
whole-host latency or proof that mobile freezing is fixed.

## Installed TEST verification and limits

The same finite probe executes the actual installed 7.3.13 and 7.3.14 service
constructors against synthetic inventories, source callbacks and inputs. It
uses the installed parser and index logic rather than the modeled YAML parser
in the scratch replay. It performs no real source I/O, writes, metadata/cache
source reads or listener installations. Every fixture retains its complete
index/input parity and identical N source reads/N index operations/one inventory.
Live GCM maps and all eight consumers' instances/settings/saved data/enabled
state are unchanged.

| Installed constructor first verification | 7.3.13 | 7.3.14 |
| --- | ---: | ---: |
| 1,000 files: total verification | 94.6 ms | 95.6 ms |
| Same fixture: helper tasks / heartbeat ticks | 0 / 0 | 11 / 11 |
| Same fixture: longest heartbeat gap | 94.6 ms | 9.1 ms |
| 10,000 files: total verification | 953.1 ms | 637.8 ms |
| Same fixture: helper tasks / heartbeat ticks | 0 / 0 | 77 / 77 |
| Same fixture: longest heartbeat gap | 953.2 ms | 9.4 ms |

The installed warm one-edit replay still reads and indexes one source. At
1,000 files it takes 1.8 ms with zero tasks; at 10,000 files it takes 12 ms,
one real task/heartbeat tick and a longest gap of 8.1 ms. The latter legitimately
crosses the elapsed budget; it is not the cheaper zero-task synthetic warm
sample. These are single hidden/unfocused-host samples, not proof of lower
total CPU work, a physical UI result or a whole-process cold-start benchmark.

The targeted warm reload preserves exactly 16,662 Markdown paths before/after,
2,733 GCM/182 Health records, all eight consumers' saved data/settings/enabled
state and the original leaf, with zero mutations. Current hidden-host samples
are 459.2 ms onload return, 721.4 ms complete API readiness, 888.7 ms Health
readiness and 222.1 ms longest heartbeat gap. Its corpus differs from the prior
warm-reload measurement, so no paired warm improvement is claimed.

All 13 installed Live Preview phases pass six tab switches and two remounts.
Up to 24 food/39 activity rows are observed, with zero measured long tasks,
phase/render errors or note-mutation attempts. The three UUID fixtures are
exact-byte archived with zero cleanup errors; settings/workouts and all eight
saved-data files stay unchanged. Only the first busy combined phase records
one required Navigator getMarkdownFiles inventory, without getFiles; zero
navigation scans are not claimed. All windows were hidden/unfocused. Reading,
foreground input-to-paint, physical mobile/Windows and whole-process cold
performance remain unverified.
