# TPS Global Context Menu

Reusable note and task context menu surfaces for the vault, plus inline note chrome such as title icons, stacked properties, note references, reminders, and mobile navigation affordances.

## Title Rendering and Filename Ownership

- GCM treats frontmatter `title` as the user-facing note name and the physical filename as derived storage.
- Rendered inline internal links that would normally show the target filename are rewritten in the rendered DOM to show the target note's frontmatter `title` when one exists. The underlying link target is not changed.
- Markdown note inline titles render frontmatter `title` plus the resolved icon in Reading and Live Preview modes. Strict Source mode keeps Obsidian's normal filename display and suppresses the title icon so the editor header stays literal.
- The note inline title in reading mode displays frontmatter `title`; clicking it opens a title edit modal instead of Obsidian's filename rename flow.
- GCM's `Rename Title` action writes frontmatter `title`. When auto-rename is enabled, `FileNamingService` then derives the physical filename from `title` plus `scheduled`, preserving scheduled date prefix behavior.
- When `scheduled` is removed from a note, auto-rename treats the persisted frontmatter as intentionally unscheduled even if Obsidian's metadata cache still has the old value, so the next title/filename sync removes the stale scheduled date marker from the filename.
- Commands are available to repair missing frontmatter titles from filenames and to reconcile the active note filename from the current title/scheduled values.
- Raw filename moves/renames should remain limited to folder moves, archive/unarchive, duplicate/create flows, and the auto-rename service.

## Mobile Header Persistence

- Mobile swipe/gesture collapse is intended to hide floating controls, including the persistent action bar, inline hovering property strips, daily-note bottom navigation, base preview property overlays, and other transient panels.
- External parent-nav actions are rendered with stable plugin/action data attributes. Invisible external actions are `display: none` while resolving and are removed when their visibility callback returns false, so mobile bottom navigation does not reserve empty rounded slots for unavailable actions.
- Mobile bottom navigation renders external integration actions even when the full parent-nav placement is configured for the top/desktop note chrome.
- On phone layouts with property chips, external integration actions are injected directly into the mobile action bar next to native actions instead of the hidden bottom parent-nav row.
- Persistent note header content remains visible while scrolling: title icons and GCM-rendered stacked properties under the title are not hidden by keyboard or gesture-collapse state.
- Stacked properties remain visible while editing on mobile; keyboard suppression only hides floating/hovering chrome and top navigation wrappers that do not contain stacked properties.
- Keyboard suppression still hides floating menu surfaces so editable fields are not covered by action bars or popovers.
- The hidden task reveal button remains mounted while editing; the quiet edit window prevents unnecessary remounting but does not suppress the button.
- Mobile reading mode is treated as a first-class rendered surface, including `.markdown-reading-view`, so hidden task lines get the same fixed reveal button and tap handling as preview/rendered views.
- `Persist task reveal state to frontmatter` is off by default. When enabled, `Show completed` and `Show tasks` write note-level state to the configured `gcmTaskVisibility` frontmatter property instead of using only temporary per-view reveal state.
- `gcmTaskVisibility.showCompleted` stores the completed-task reveal state, and `gcmTaskVisibility.showTasks` stores the reading-mode all-task reveal state. When the setting is disabled, no frontmatter is written and the reveal buttons keep their temporary/resetting behavior.
- Inline and stacked property tag chips render only note-level frontmatter tags from `tags` / `tag`; body hashtags and task-line hashtags remain searchable content but are not shown as note property values.
- Custom property visibility is key-aware:
  - `Always show`: render regardless of frontmatter.
  - `Only when key has value`: render only when the key exists and is non-empty.
  - `Only when key exists`: render when the key exists, even if its value is empty.
  - `Only when key exists but is empty`: render only when the key exists and has no value.
  - `Only when key is missing`: render only when the key does not exist.
  - `Only when missing or empty`: legacy empty behavior; render when there is no populated value.
  - `Never show`: hide the configured property even when the note has a key and value.
- `Inline visibility` and `Context menu visibility` can override the default property visibility independently. For example, a property can use `Inline visibility: Only when key exists` and `Context menu visibility: Always show`, so missing keys stay out of the inline chip row but remain available from right-click actions.
- Completing a note from outside GCM-owned controls is watched through vault/metadata events. If a note status transitions into `complete`/`completed`/`done` from native Properties, Bases, Kanban, calendar/reminder surfaces, or another plugin, GCM runs the same open-checklist guard and reverts the status if the prompt is canceled.
- The external completion guard is user-facing and is not suppressed by the mobile/background-automation gate, so iPad and mobile completion actions still prompt when a note has open checklist items.

## Advanced Canvas Properties

- `.canvas` files are property targets when Advanced Canvas metadata compatibility is enabled.
- GCM reads canvas frontmatter through `CanvasPropertiesService`, which mirrors Advanced Canvas' `metadata.frontmatter` shape instead of relying only on Obsidian's cached metadata.
- GCM writes canvas property edits through the shared frontmatter mutation path, which delegates `.canvas` files to the Advanced Canvas bridge and falls back to the compatibility JSON shape if the patched writer does not refresh metadata in time.
- Right-clicking a canvas item resolves to the active `.canvas` file so Advanced Canvas file-level properties can be edited from GCM instead of accidentally writing to a linked note.
- GCM also injects into Advanced Canvas' native `canvas:node-menu` event, because canvas item right-clicks do not reliably flow through Obsidian's normal `file-menu` / `editor-menu` hooks.

## Task-Line Context Menus

- GCM owns context-menu actions for rendered task rows from Kanban and Calendar surfaces.
- Task-line settings are grouped under `Workflows > Task Lines`, including task hiding/reveal behavior, task status-to-checkbox reconciliation, linked child-note checkbox rows, checklist completion warnings, and checklist promotion behavior.
- `Task hiding exclusions` defaults to no exclusions. Matching files and folders bypass completed-task hiding, reading-mode all-task hiding, and reveal buttons; patterns use the same exact path, folder prefix, wildcard, `name:<basename>`, and `re:<regex>` syntax as other GCM exclusion settings. `Inbox/` is an example/local vault configuration, not the product default.
- Long-pressing an inline task checkbox keeps the checkbox-state choices first, then appends GCM task-line actions such as title editing, inline property edits, opening the task line, moving the task to another file, deleting the task, and time tracking.
- Reading-mode task rows resolve source lines from rendered `data-line` metadata as zero-based candidates and validate the candidate against the clicked row text before opening the menu, so repeated checklist rows do not default to the first task.
- Task-line context menus apply a temporary active-line highlight in reading mode and Live Preview while the menu is open. Highlights are scoped to editor lines, rendered task list items, and explicit TPS Calendar/Kanban task row elements so broad note/list wrappers are never painted. Cmd/Ctrl-click toggles task-line selection within the current note; right-clicking a selected task exposes batch-safe actions for selected tasks, including status changes, adding a tag, archive-in-place, move-to-different-file, delete, and clearing selection. Single-task modal actions remain single-task only.
- When a rendered card's stored line number is stale, GCM falls back by matching clean task-title variants instead of the full rendered metadata string, so chips like scheduled date, status, time, and all-day flags do not prevent resolving the source checklist line.
- Moving a task line from a Daily Note to another Markdown file preserves the Daily Note as a scratchpad/inbox record. GCM inserts the original task block into the target file unchanged, then keeps the Daily Note block in place with the checkbox marked, `[completedDate:: null]`, struck-through task block content, and a simple `%% Moved to ... on ... %%` comment. Non-Daily Note moves keep the normal destructive move semantics.
- GCM-created task lines add inline created/modified timestamp fields using the configured `dateCreatedFrontmatterKey`, `dateModifiedFrontmatterKey`, and `fileTimestampFormat` settings. GCM task-line mutations update the configured modified timestamp, while task completion still adds or removes inline `completedDate` based on the checkbox/completion marker.
- Reserved TPS inline metadata such as `tpsInlineProps` / `tps-inline-props` is always hidden in Live Preview and Reading View. Visible task chips are limited to configured user-facing inline properties.
- Removed settings: subitem path/status/priority defaults, new-subitem visual metadata seeding, Bases icon helper-field writes, and native Properties-under-title rendering. New subitem notes default to the parent note folder, or vault root when there is no parent folder, and no longer receive default status/priority solely from removed settings. Normal icon/color rule fields still write through Notebook Navigator rules.
- Settings normalization: child-status checkbox mappings now preserve default icon/label metadata when edited through the textarea setting, empty/invalid parent body-link format values normalize back to `wikilink`, legacy top-level Notebook Navigator smart-sort payloads are migrated into the nested canonical `notebookNavigatorRules.smartSort.buckets` shape on load/save, Notebook Navigator icon/color rule filtering now matches exact case-insensitive field values such as `working`, and Daily Notes / Recurrence child settings collapse immediately when their parent feature toggle is disabled.

## Time Tracking And Active Pins

- `Auto-pin active notes` keeps matching notes open and pinned while they are active. GCM only unpins tabs it pinned itself.
- A note is active when the note itself has a running note-level time-tracking session, when its note-level `scheduled` value is inside its scheduled window, or when it matches an `Auto-pin frontmatter rules` entry. Task-line scheduled values and task-line timers do not make their containing note active for auto-pin.
- Starting, stopping, pausing, or resyncing running timers immediately refreshes active-note pins so timer targets do not wait for the scheduled metadata scanner.
- Auto-open uses GCM's normal file-open path with `active: false` and `revealLeaf: true`, so timer/scheduled targets are opened and pinned without intentionally stealing editor focus. If the user closes a still-active auto-pinned note, the next auto-pin evaluation reopens it and shows a Notice explaining the reason.
- Explicit note opens avoid replacing a pinned tab with a different file and re-resolve the actual opened leaf before focusing/revealing it. This prevents pinned active-note tabs from blocking Notebook Navigator or TPS note-open actions. When a pinned file is the source context, missing target notes open in a new tab; existing target tabs are focused/revealed.
- Normal app-level note opens reuse and focus an existing open tab for the target file. If the target file is not already open, GCM creates a new focused tab instead of replacing the current tab. Background opens, explicit same-leaf operations, sidebars, and hover previews keep their specialized behavior.
- Notebook Navigator and other native note-open callers share the same default opener. Repeated open calls for the same target are coalesced while the first tab is still loading, and GCM recognizes pending markdown view state as an existing target tab so clicks focus the target instead of creating duplicates.
- Title sync preserves meaningful previous titles and basenames in `aliases` when GCM changes frontmatter `title`, without replacing existing aliases. Markdown heading typing offers note suggestions from frontmatter title, filename, and aliases; choosing one replaces the typed heading text with a wiki link while preserving the heading level.

## Base Link Preview Preference

- `Force previews for Base links` is exposed through the GCM plugin API so Calendar Base and Kanban use the same preference.
- With `Force previews for Base links` enabled, Base-backed note links still use first-click Hover Editor preview behavior. If the source Base/note tab is pinned, the second click opens the target in a new tab instead of replacing the pinned tab.
- When the setting is disabled, Calendar/Kanban Base clicks should open/focus notes normally instead of emitting Obsidian `hover-link` preview events.
- When scheduling a note-level `scheduled` property, GCM warns if the note contains checkbox tasks scheduled on multiple other days. The write is allowed, but the warning flags likely storage/inbox notes such as calendar task lists.

## Sidebar Commands

- `Open active file in Left Sidebar` and `Open active file in Right Sidebar` resolve existing copies only within the requested side dock. If the active file is already open in the main editor, the command still opens or reveals a side-dock copy instead of focusing the main editor leaf.
- Side-dock opens use inactive file loading and then reveal the requested sidebar, so the command does not intentionally steal editor focus while placing the note in the requested side.

## Status Classification

- GCM owns status normalization and exposes active vs non-active status classification to integrations.
- `Active Status Values` defaults to `todo, working, holding`. Integrations such as TPS Calendar Base should treat configured status options not in that active set as non-active for styling, while recurrence still uses `Completion Triggers`.
- Active status values take precedence for integration classification, so an older recurrence completion setting cannot make an explicitly active status such as `holding` render as completed in Calendar.

## Virtual Base Embeds

- GCM can read note-level frontmatter properties that point at `.base` files and virtually render those Bases inside the note without modifying the note body.
- These are plain frontmatter properties, not GCM custom properties. They can be edited with Obsidian's normal properties UI or other metadata tooling.
- Default keys:
  - `gcmBaseTop`: embeds one or more Bases near the top of the note.
  - `gcmBaseBottom`: embeds one or more Bases near the bottom of the note.
  - `gcmBaseHover`: embeds one or more Bases in a sticky panel that follows scrolling under the note header chrome.
- Values may be a single path/link or a list, for example `[[Related Tasks.base]]`, `Related Tasks`, or YAML list entries.
- The hover placement uses the same mobile suppression behavior as other floating GCM chrome: it hides during swipe collapse or keyboard editing, while normal top/bottom virtual embeds stay in the document flow.
- Virtual Base embeds use Obsidian's normal rendered `![[*.base]]` path. Each referenced Base is rendered as its own virtual item. Top and bottom placements stay unframed and in the note flow so they read like normal embedded note content; empty non-interactive Base items and inline empty-state panes collapse instead of reserving a tall blank pane, but embedded Kanban boards remain visible even when their current result count is zero. GCM mounts into visible reading and Live Preview surfaces, and it remounts if Obsidian replaces the rendered DOM during scroll/layout refresh. It neutralizes TPS Kanban's normal reading-embed vertical transform inside virtual Base hosts so embedded lanes stay in the host instead of jumping behind the note header. Hover placement is the only bounded floating panel.
- Current defaults are configured in code through `enableVirtualBaseEmbeds` and `virtualBaseEmbedProperties`; invalid saved entries are normalized back to the three default placements.
