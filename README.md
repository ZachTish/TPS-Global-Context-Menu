# TPS Global Context Menu

## 1.30.0

- GCM now owns native properties for Canvas, Base, PDF, media, and every other non-Markdown vault file without Advanced Canvas. It never changes the source file's bytes; properties live in a lazily created Markdown companion under `_assets/TPS File Properties` so Obsidian Properties and Bases can index them normally.
- Native Bases can form an active asset catalog by requiring `tpsGcmFileProperties == 1`, excluding `tpsGcmSourceMissing == true`, excluding nonempty `tpsGcmTombstonedAt`, and showing `tpsGcmSource` as the source link. Native `file.*` values still describe the companion. GCM's TPS List instead projects the logical source file and deduplicates source-plus-companion results while retaining the configured order.
- Stable file IDs and reserved source metadata follow non-Markdown file and folder renames. Deleted sources retain their properties without a live source link; **Relink** deliberately attaches that retained identity to a replacement, while **Start fresh** tombstones the retained record and creates a separate identity. Duplicate or conflicting identities fail closed.
- A non-Markdown-to-Markdown type transition retains the companion with an explicit pending-target/needs-merge marker instead of silently writing its values into the Markdown file. The relink flow surfaces that state; a future explicit merge is required.
- Legacy Canvas `metadata.frontmatter` imports are copy-only, either through the explicit import command or lazily on the first GCM mutation. Canvas JSON is never cleaned up or synchronized back. Public integrations use `fileProperties` v1; the former `canvasProperties` surface remains as a deprecated compatibility alias.
- Property updates publish a redacted `tps:gcm-file-properties-updated` payload containing paths, item ID, action, changed key names, and optional surface, but no property values. Direct user actions also emit GCM's explicit-action signal; omitted public API provenance defaults to automation and emits only general file/property invalidation.
- Non-Markdown files can participate as parents or children through the same logical properties, including the configured exact key/value parent-child ignore rule. The whole managed companion root is reserved and is excluded from ordinary file-property, task, recurrence, relationship, and note workflows.
- Item History v1 remains task-only; a future asset-history v2 can use `tpsGcmFileId`. TPS Notebook Navigator rules can consume GCM's logical properties, but Navigator's own rows, search, and property tree do not yet project companion values. Minimum supported Obsidian remains 1.10.0. Validation passed 1,078 declared tests, the focused 187-test native-property matrix, TypeScript, a separate production build, exact source/runtime artifact comparison, and live test-vault companion/Base/rename QA; hashes are recorded in `release-notes/1.30.0.md`.

- Linked context now observes its owning Markdown view and recovers when Obsidian replaces a Reading View or Live Preview mount during scrolling. Source-note edits, renames, and deletions invalidate the affected target panel so stale or detached cards do not linger.
- **Ignore matching parent/child notes** adds an off-by-default exact frontmatter key/value rule. Matching parents and children are excluded from discovery, panels, linking, linked-checkbox mutation, status synchronization, and relationship automation without deleting existing body links or frontmatter relationships.

Complete, won't-do, and migrated task rows follow the same setting inside Linked context; a single terminal task card disappears as a unit while mixed excerpts retain their nonterminal content.
- Note-linked time tracking no longer writes or removes note-level `scheduled`, `timeEstimate`, or end metadata. Task-linked sessions still synchronize those values on the exact task line, and every session still creates or reuses its `## Time Tracking` workspace in the session-start Daily Note.
- This backward-compatible minor release adds optional settings choices and performs no bulk note migration. Existing linked-context, parent/child, task-hiding, tag, and time-tracking defaults remain compatible; minimum supported Obsidian remains 1.10.0. Final validation and artifact hashes are recorded in `release-notes/1.29.0.md` after the versioned build is complete.

## 1.28.0

- **Workflows → Tasks → After moving a task from a Daily Note** now chooses the source disposition for GCM-owned and compatible cross-plugin moves. **Keep a migrated marker** remains the backward-compatible default; **Remove the source block** deletes the complete source task block after the destination write is confirmed.
- Task API v3 adds the explicit `configured-daily-note` source policy. Legacy `remove` and `migrate-if-daily-note` requests keep their exact prior meanings, so existing callers are not silently reinterpreted. TPS Controller 0.4.2 uses v3 for the notification sidebar's reminder move and fails closed with an older GCM API.
- GCM now maintains a local, vault-scoped item-history journal for committed direct-user task actions. Status, priority, tags, checkbox state, create, edit, move/migrate, and delete events retain a stable `tpsId`, action origin, before/after locators, and confirmed source disposition for a future item-history modal.
- The journal is deliberately redacted: it stores canonical checkbox/status/priority/tag state and a generic changed marker for other text edits. Vault-relative before/after paths are retained so a future modal can locate current or deleted items, but raw task lines, task titles/content, note bodies, arbitrary inline fields, external IDs, and links/URLs are never stored. Missing user provenance and background automation are not journaled.
- A pending intent is written before a tracked mutation, its identity is injected in the same guarded content write, and the event is committed only after the write is confirmed. Canceled, unchanged, stale, ambiguous, rolled-back, or unconfirmed writes abort or remain short-lived uncertain evidence rather than becoming successful history; history failures never roll back a valid content edit.
- **Keep local item history** defaults on. Retention defaults to 90 days and is bounded to one year, 25,000 events across the vault, 200 per task, and 24 hours for unresolved pending intents. Turning recording off preserves existing history for later query or clearing; the datastore stays on the current device and is not written into notes.
- Task API v3 mutations accept an optional explicit user cause, return `stableId`, and expose a versioned `history` v1 surface for entity resolution, bounded query, stats, pruning, and clearing. Calls without a user cause remain unjournaled for compatibility.
- Reloading GCM with TPS Home already open now initializes Home action routing before Obsidian restores the persisted view, so configured component actions render safely during plugin reload.
- This is a backward-compatible minor release with additive settings and APIs. Existing notes are not bulk-migrated; a surviving task receives a stable identity only within its first tracked mutation. Minimum supported Obsidian remains 1.10.0. Final validation and artifact hashes are recorded in `release-notes/1.28.0.md`.

## 1.27.0

- TPS Table and TPS List now share a complete typed field contract for text, number, datetime, snooze, selector, list, tag, link/entity, checkbox, Kind, recurrence, Folder, and formula values. Editors route through the appropriate picker or modal, invalid numbers are refused, checkboxes can be cleared, and formula/source metadata stays read-only.
- Sorting and grouping compare numbers, dates, booleans, lists, links, and formula results by their typed meaning instead of flattened display text. Both view types expose **Items with multiple values**: the default **Show in every matching group** fans a row into each value, while **Show in one combined group** keeps it in one deterministic lane.
- Table filters now fail closed with a visible diagnostic when syntax, an operator, an index, or a formula cannot be evaluated. Filter-derived task, bullet, heading, and note creation uses the same exact whole-Base plus active-view contract and refuses an unverifiable candidate before writing.
- Configured property keys are case-insensitive exact identifiers: edge whitespace is ignored, but punctuation and interior spaces remain meaningful, so `client-id`, `client_id`, and `client id` do not collide. Settings identify blank or duplicate keys without renaming saved definitions, and newly added fields receive a unique default key.
- Repeated inline carriers are aggregated for display, filtering, sorting, grouping, editing, and TPS List lane drops. List membership is matched exactly, including nested or comma-bearing wikilinks; a successful mutation preserves unrelated members and canonicalizes only the edited property to one carrier.
- TPS Table range/toggle selection now forms a canonical task-only batch. Task context menus receive only the currently rendered selected task revisions; bullets, headings, generic records, and mixed selections remain safely scoped to the clicked row. Table and List selections are reconciled on every rerender so removed or replaced rows cannot inherit stale selection.
- TPS List task rows support real desktop pointer drag and mobile long-press drag between writable groups. Touch drag activates after 550 ms with 10 px movement tolerance so normal scrolling cancels before pointer capture, and every drop re-resolves the exact unique source revision before changing the line.
- Folder fields consistently describe the containing note's source folder and are read-only on synthesized lines. Kind remains additive across structural and explicitly authored identity, including native-note reconciliation for bare Kind and configured Folder filters that Obsidian's native pass cannot represent by itself.
- Native and GCM checkbox changes now share completed-date reconciliation, while task status writes retain the configured checkbox mapping guard. Stale, missing, or duplicate exact line revisions fail closed across cell editors, quick editors, menus, deletes, moves, and drag/drop.
- TPS Table reuses revision-keyed Markdown scans across unchanged rerenders and bounds cold source reads to eight concurrent files. Totals explicitly exclude `file.*` and `line.*` metadata aliases in addition to dates, IDs, units, and mixed columns.
- This backward-compatible minor release adds the per-view multi-value grouping choice but performs no automatic note or setting migration. Whole-note recurrence remains intentionally read-only in TPS List cells so the canonical recurrence lifecycle is not bypassed; task-line recurrence remains editable. Minimum supported Obsidian remains 1.10.0. Final validation and artifact hashes are recorded in `release-notes/1.27.0.md` after the versioned build is complete.

## Title Rendering and Filename Ownership

- GCM treats frontmatter `title` as the user-facing note name and the physical filename as derived storage.
- Rendered inline internal links that would normally show the target filename are rewritten in the rendered DOM to show the target note's frontmatter `title` when one exists. The underlying link target is not changed.
- Markdown note inline titles render frontmatter `title` plus the resolved icon in Reading and Live Preview modes. Strict Source mode keeps Obsidian's normal filename display and suppresses the title icon so the editor header stays literal.
- The note inline title displays frontmatter `title` in rendered modes, and clicking the title inside a Markdown note opens GCM's title edit modal directly. This click path does not depend on a delayed title-render refresh, so newly opened notes can still be renamed from the title immediately.
- Note context menus and the persistent-panel options menu expose one clickable `Title: <display name>` row. Link syntax is unwrapped for presentation, the editor writes frontmatter `title`, and—when auto-rename is enabled—`FileNamingService` derives the physical filename from `title` plus `scheduled` while Obsidian retains link ownership.
- Daily Notes are the intentional exception to title-derived filenames: Core, persisted, and Periodic Notes paths keep their configured date filename while preserving a nonblank template/user `title` or `Title`. Daily Note kind/type/tag markers provide the same protection, and only a missing or blank title receives a filename-derived fallback.
- When `scheduled` is removed from a note, auto-rename treats the persisted frontmatter as intentionally unscheduled even if Obsidian's metadata cache still has the old value, so the next title/filename sync removes the stale scheduled date marker from the filename.
- Title and filename maintenance is handled by the live title-sync services and settings-backed repair paths rather than extra command-palette maintenance actions.
- Raw filename moves/renames should remain limited to folder moves, archive/unarchive, duplicate/create flows, and the auto-rename service.
- Both the global/native context menu and persistent-panel `Archive` actions move selected files directly into the effective archive folder. When TPS Controller is loaded, GCM uses Controller's two-stage archive `sourceFolder` as the first-level archive target, so Controller can later move those files onward to the cold archive destination. Markdown files receive the configured archive tag and `archiveOriginalFolder` when that metadata write succeeds; `.base`, `.canvas`, and other non-Markdown files move without frontmatter/tag edits. Tagging is never a prerequisite for the move.

## Agent API Contract

GCM exposes deterministic Task API v3 operations through `plugin.api.tasks`. Agent-facing calls should use these APIs rather than command-palette automation or natural-language command strings. Mutating calls require stable, auditable references such as vault file path plus line number/raw line, and return structured before/after records. `tasks.version` is `3`; task records expose `stableId` from `tpsId` or the compatible `subitemId` alias, never from recurrence identity.

Stable task operations:

- `tasks.create({ title, targetPath, fields, tags })` creates one explicit task line in one explicit target note.
- `tasks.get({ path, line, rawLine })` resolves one task line. `line` is 1-based; `lineNumber` is 0-based.
- `tasks.update({ path, line, rawLine }, { title, checkbox, status, fields, addTags, removeTags })` mutates only the resolved line.
- `tasks.setCompletion({ path, line, rawLine }, completed)` maps a binary completion value through the configured Complete/Todo markers and runs GCM's canonical checkbox follow-up.
- `tasks.setScheduled({ path, line, rawLine }, scheduled)` writes or clears the task-line `scheduled` inline field.
- `tasks.setField({ path, line, rawLine }, property, value)` writes or clears one explicit inline field on the resolved task line.
- `tasks.setFields({ path, line, rawLine }, fields)` writes or clears multiple explicit inline fields on the resolved task line.
- `tasks.move({ path, line, rawLine }, { targetPath, placement, sourcePolicy, resolution })` moves the complete task block. Omitting `placement`, or using `end`, retains the append-to-end default; `after-frontmatter` inserts immediately after a valid opening YAML frontmatter block; `line` uses the supplied one-based `line` or zero-based `lineNumber`. `sourcePolicy: configured-daily-note` follows the user's Daily Note source setting, while legacy `remove` and `migrate-if-daily-note` remain explicit and stable.
- `tasks.delete({ path, line, rawLine })` removes the resolved complete task block.
- `tasks.focus({ path, line, rawLine })` opens and focuses the resolved task line and returns a boolean outcome.
- `tasks.list({ paths, pathPrefix, fields, tags, status, includeCompleted })` queries eligible task lines without mutating them. Frontmatter and protected Markdown blocks are never task results.
- `tasks.findByField(property, value, filter)` queries existing task lines by one explicit inline field.

Every mutating Task API v3 method accepts an optional final user-cause argument such as `{ kind: 'user', sourcePluginId: 'tps-controller', surface: 'notification-sidebar' }`. A valid explicit cause enables local history for that committed action; an omitted or invalid cause preserves the unjournaled automation/API behavior. Content mutation remains fail-open if the private history store is unavailable.

`plugin.api.history` is version `1` and provides `resolveEntity(reference)`, `query(reference, { limit, before, beforeEventId })`, `stats()`, `prune()`, and `clear()`. Query references may use a stable entity ID or a live task path/zero-based line/raw-line reference. For stable pagination, pass the last event's `occurredAt` as `before` and its `eventId` as `beforeEventId`; this retains events that share the same millisecond. Results contain only the redacted event schema and vault-relative locators; raw note or task text is never returned because it is never persisted. History is local to the current vault/device, defaults to 90-day retention, and remains available to query or clear when new recording is disabled. History v1 intentionally excludes whole-note/frontmatter events, AI-assisted creation and background automation, time-tracking session bookkeeping, raw editor typing and editor-only line commands without a durable vault-write confirmation, cross-device synchronization, and the future visual history modal.

Move callers that must preserve a Daily Note source pass `sourcePolicy: "migrate-if-daily-note"`; the default `remove` policy preserves Task API v1 behavior. `resolution: "exact-or-identity"` accepts only the exact raw source line or its stable `tpsId`/`subitemId` identity and never falls through to a unique fuzzy title. The result truth table is authoritative: `ok: true, changed: true` means the move committed (the refreshed `task` may be `null` if post-commit refresh failed); `ok: true, changed: false` is a same-file no-op; `ok: false, changed: false` means no mutation remains; and `ok: false, changed: true` reports a conflicting/partial state that the caller must surface without an automatic retry or fallback. Destination-first writes are rolled back only when the exact expected destination snapshot is still present.

Path strings and file objects are canonicalized through GCM's own vault before use. Callers may pass an Obsidian file object from another plugin realm; GCM uses its path rather than relying on constructor identity. Explicit create or move targets that do not resolve to an existing Markdown file are rejected instead of falling back to another note.

Diagnostics:

- `diagnostics.getOpenerDecision(targetPath?)` returns the active file, matching target leaf, and markdown leaf summaries without mutating workspace state.
- When debug logging is enabled, Task API and bulk-edit mutations log high-level cause/result events: create/update/move/delete starts, unresolved targets, selected paths/line numbers, changed/no-change outcomes, protected-key blocks, checklist/recurrence guard cancellations, and per-file mutation failures. These logs are intended to explain reports like "the task checkbox changed in one surface but not the note", "a task moved to the wrong file", or "a status update was blocked."
- Vault-delete relationship cleanup uses the deleted note's canonical full path, including extensionless, aliased, headed, markdown, and relative link forms. Basename-only links are removed only when no other same-basename note remains; ambiguous references are preserved. Bulk-delete sweeps run serially, and body-link removals use Obsidian's atomic `Vault.process` mutation so a concurrent note edit cannot be overwritten by a stale whole-file write. Debug output reports queued sweeps, scanned/touched counts, removed references, preserved ambiguity, and failures without logging note bodies.
- Rendered inline-property edits report atomic exact-line, uniquely relocated-line, conflict, and write-failure outcomes using only the file path and line numbers. Source-line content and property values are not logged.
- Context-target resolution logs one concise decision per menu action with the selected source (`canvas`, `kanban`, explicit files, embed, explorer, active file, or none), file count, representative paths, fallback state, and Notebook Navigator selection source counts. These logs are intended to explain reports like "I right-clicked this item but the action used a different note" or "the menu did nothing from this surface."

Agent integrations must not use fuzzy task titles or broad search results as mutation targets. If an agent needs to modify a line, it should first resolve or receive the exact `path`, `line`, and preferably `rawLine`, then pass that reference back into the API. Food and barcode-specific deterministic APIs live in TPS Health, where UPC/barcode and food-note paths are the stable identifiers.

### Entity index and Kind references

The registry is intentionally named `entityIndex` in code and API. **Kind** is one indexed dimension rather than the registry itself, leaving the same engine available to future plugins and dimensions.

To register entities and constrain a reference:

1. Under **Rules & fields → Custom fields**, keep or create a field whose type is **Kind (Entity identity)**. Its configured key—normally `kind`—is indexed.
2. Give a Markdown note a matching frontmatter value such as `kind: project`, or put the configured inline field on a Markdown task, bullet, or ATX heading such as `[kind:: project]`. Scalar and YAML-list note values are supported.
3. On another custom field, set **Accepted kinds** to one identity such as `project`, or enter several comma/newline-separated identities such as `project, area`. Multiple accepted Kinds are combined as OR. Use a scalar field for one relationship or a list field for several relationships.
4. Choose the field's **Value sources**. Use **Entities only** for a strict relation, or combine Entities with Manual and/or Vault values when the same field must retain controlled literals.
5. In any supported property editor, choose from the matching project notes and project lines. Notes store `[[path|title]]`; lines store `[[path#^block-id|title]]`.

Base row shape and explicit identity remain distinct, except for the intentional additive `task` union. In TPS List, `kind == task` can therefore include both Markdown checkbox rows and native notes whose configured Kind property equals `task`. Entity properties accepting Kind `task` likewise offer every checkbox line plus notes or other line entities that explicitly carry that value. A checkbox with `[entityKind:: project]` is both structurally `task` and explicitly `project`; neither identity overwrites the other, and GCM never persists an implicit `[kind:: task]`. `kind == bullet`, `kind == header`, and `kind == h1` through `h6` remain structural row filters; bullets/headings become entities only through an explicit configured inline Kind. Kind identity values can be edited from their configured Base cells and line context menus, while the compact task quick editor keeps identity fields out of its task-property form.

The note index builds lazily from Obsidian's metadata cache. Content-backed task, bullet, and heading entities are added by `ensureReady()`/`queryAsync()` and then updated incrementally. Queries are case-insensitive exact matches by dimension, deterministically sorted, immutable, and cached until the index revision changes. Renames replace old paths, deletes remove source records, GCM writes invalidate immediately, and later readiness calls retry transient file-read failures.

```js
const gcm = app.plugins.getPlugin("tps-global-context-menu");

// Includes matching notes and addressable task/bullet/heading lines.
const projects = await gcm.api.entityIndex.queryAsync({
  dimensions: { kind: { anyOf: ["project"] } },
});

// Version-1 compatibility: synchronous query() remains note-only.
const projectNotes = gcm.api.entityIndex.query({
  dimensions: { kind: { anyOf: ["project"] } },
});

const unregister = gcm.api.entityIndex.registerDimension({
  name: "lifecycle",
  propertyKeys: ["state"],
});
```

`entityIndex.version` is `3`. `query()` always returns its backward-compatible synchronous note-only view, even after content readiness; `queryAsync()` awaits a complete line index and returns notes plus lines or rejects with `entity-index-incomplete` and the failed source paths. `ensureReady()` prepares the same complete block-aware snapshot. Async consumers can scope results with `entityTypes` (`note` and/or `block`) and structural `lineKinds` (`task`, `bullet`, or `heading`) in addition to `dimensions`/`allOf`, `anyOf`, `noneOf`, `search`, and `limit`. Version-3 consumers must fail closed when readiness rejects; they must not treat a partial or empty snapshot as authoritative.

`getById`, note-only `getByPath`, `getByLocator`, `getByReferenceTarget`, `getBySourcePath`, `materializeReference`, `getDimensionValues`, `getRevision`, `onChanged`, and `invalidate` are public. Records expose `entityType`, `sourcePath`, `lineKind`, `lineNumber`, `referenceState`, `subpath`, `blockId`, `locatorKey`, and `referenceTarget`. Block records may additionally expose immutable `lineProperties`, keyed by first-authored inline-field casing with ordered string arrays that preserve repeats and blanks; note records omit it. `materializeReference()` returns a note unchanged and atomically re-resolves a provisional line. `registerDimension` returns an unregister callback; external dimensions remain registered when GCM's custom-field configuration changes.

Line entities are selectable only when they can produce a stable native block reference. A line that has no block ID remains provisional until selection, when GCM atomically re-resolves the exact source and appends one collision-checked ID. Ambiguous duplicate IDs, duplicate legacy identities, stale lines, entities that changed Kind while a picker was open, and formerly valid lines moved into protected Markdown fail closed. The picker rechecks existence and accepted Kind immediately before writing. Ordinary paragraphs, YAML frontmatter, fenced or indented code, HTML/comment blocks, Canvas records, and non-Markdown files are not indexed as lines. Field- or tag-shaped text inside closed inline code or protected TPS JSON is never treated as identity or editable metadata; unsafe paths that cannot be represented inside both a wikilink and GCM's hidden carrier are omitted from constrained pickers.

Constraints govern the entity lane, not destructive migration. Existing out-of-Kind links remain visible and stored until the user changes them. Scalar fields store one selected value; entity selections use one canonical link. Lists preserve their configured storage, deduplicate canonical entity targets, and can safely mix literal values with entity links when their source mode allows both. Entities-only pickers have no free-text escape hatch and never create entities implicitly.

TPS Table and TPS List use the same source-aware picker for empty and populated Projects, Contexts, Status, and other configured cells. The same fields use that contract from configured right-click menus on notes, tasks, bullets, headings, and TPS Table line records. A writable arbitrary Base column that is not in the custom-field registry still opens a guarded scalar editor instead of navigating away. Built-in `tag`/`tags` cells display and toggle the semantic union of visible hashtags, `[tag:: …]`, and `[tags:: …]`; custom tag fields stay isolated, and the picker offers known vault tags rather than creating arbitrary values. `scheduled` cells use the standard scheduling modal and manage `scheduled`, `timeEstimate`, and true-only `allDay`; unrelated datetime properties do not acquire schedule companions. Line edits use guarded exact-line atomic writes and preserve indentation, newline style, final-newline state, native block IDs, unrelated inline fields, and protected TPS JSON metadata.

### Relational Status recipe

1. Create one or more notes with frontmatter such as `kind: status`; a line entity may instead use `[entityKind:: status]` plus a stable block ID.
2. Configure `kind` and any line identity key such as `entityKind` as **Kind (Entity identity)** custom fields.
3. Configure the Status custom field with key `status`, a scalar Selector type, **Accepted kinds: status**, and **Entities only**. Enable its context-menu visibility if Status should appear on right-click.
4. In a task Base, use the `status` column/filter for the relational link and `task.status` for the checkbox workflow state. These fields can be displayed and filtered together without overwriting one another.
5. If legacy literals must remain selectable, switch Status to **Manual + entities**, **Vault + entities**, or **Manual + vault + entities**. Only the entity portion is Kind-constrained.

## TPS Table View

- GCM registers a reusable Bases view type, `tps-table`, displayed as **TPS Table**. It renders matching Markdown inline-property/bullet log lines in a compact table-shaped surface instead of requiring a domain-specific custom Base view. Legacy `tps-log-table` registration was removed so the Bases view picker shows only one TPS Table option.
- TPS Table evaluates the whole-Base filter tree and only the active TPS Table view's filter tree against each log row, with the two roots combined by an outer `and`. Ordinary `file.*` predicates select source notes while bare, `note.*`, `line.*`, and `log.*` properties resolve against inline row fields first and note frontmatter second. Nested `and`/`or`/`not`, equality, numeric/date comparisons, empty/exists, contains, starts-with, and ends-with predicates behave the same in standalone and embedded/Home surfaces. Children evaluate in stored order with normal short-circuiting: an evaluated formula failure excludes the row even inside `not` or before a later true `or` branch, while an unreachable branch after a decisive result is not run. Invalid syntax, unsupported evaluated operators or methods, unavailable indexes, and formula failures exclude the affected row and produce one visible `role="alert"` diagnostic; TPS Table never includes a row merely because its filter was unverifiable.
- Task-shaped rows synthesize query-only `status`/`checkboxStatus`, `open`/`isOpen`, and `done`/`isDone`/`completed`/`complete` fields from the Markdown checkbox. The configured linked-subitem mappings and shared status service determine each value. These aliases participate in whole-Base and active-view filters, grouping, sorting, and explicitly configured columns, but they do not crowd the inferred default columns.
- Within task-shaped rows, `tag`, `tags`, `task.tag`, and `task.tags` are equivalent and combine raw `#tags` with `[tag:: …]` and `[tags:: …]` values. Prefixes and a leading `#` are optional, and `contains` uses exact tag membership. `file.tags` addresses the containing source note instead.
- TPS Table's native `+ New` delegates to the owning view. The active-view and whole-Base filter roots form one additive creation plan: `task`, `bullet`, `header`/`heading`, and `h1` through `h6` create real Markdown structural lines in the exact `file.path`/`task.path` target. Ordered alternatives select the first satisfiable branch; status maps to the task checkbox; tags add together; deterministic date ranges choose a matching day; and exact scalar defaults become inline fields using the authored property key, including punctuation and interior whitespace. The completed candidate is checked against both filter roots before append, and an unsupported or unavailable creation-time predicate refuses the write. When no exact target filter exists, the shared Workflows → Tasks fallback uses today's Daily Note by default or one explicitly configured Markdown note; **Require a filter** remains available as an explicit fail-closed policy. Explicit invalid targets never redirect to the fallback. Views without a structural line-kind filter retain native note creation only when the complete Base definition supports it, and command overrides still take precedence.
- By default TPS Table targets lines with `[food:: ...]`; set `lineFilterKey`, `lineProperty`, or `lineFilterKeys` on the view to target another inline-property key or key set.
- Each TPS Table view has a **Totals row** option with **Off**, **Top**, and **Bottom** positions. The row sums only columns whose non-empty values are all strict numbers, explicitly excludes every `file.*` and `line.*` metadata alias as well as dates, IDs, units, and mixed-value columns, and follows the Base's already-filtered active-view result set.
- `order` or `columns` controls displayed log columns. If omitted, the view infers common log fields such as `food`, `qty`, `unit`, `cal`, `protein`, `carbs`, and `completedDate`. `sort` / `sortBy` compares numbers, dates/datetimes, booleans, list/tag members, links/entities, text, and formulas through their typed value contract; missing values retain deterministic placement.
- TPS Table follows the configured Base `order` exactly. `title`, `text`, `line`, `task.title`, and `line.text` render the canonical visible line title, including ordered tasks and Markdown/wiki-link presentation without tags, inline properties, block IDs, or protected metadata. `file.name`, `file.basename`, and `file.link` render the containing Markdown filename as a normal internal link. When a view has no explicit order, TPS Table retains its inferred inline fields plus Source and Line fallback columns.
- TPS Table honors the active view's `groupBy` for synthesized line rows. Use `file.name` to group lines by containing filename or `file.path` to group by the unique vault-relative containing-note path; `file.basename`, `file.folder`, `file.ext`/`file.extension`, `task.path`, `task.file.path`, `line.path`, and `heading.path` use the same source-note model. Filename groups intentionally merge equal filenames from different folders, while path groups keep them separate. Typed list/tag/link/formula groups expose **Items with multiple values**: the default `separate` mode renders the row in every matching group, while `combined` creates one stable comma-separated group. Group headers are read-only/non-selectable, totals remain global, and Shift-selection follows the grouped visual order.
- View-level create override: set `createAction: command` and choose `createCommandId` from the command dropdown to make the plus button run that command instead of filter-derived creation. For food logging, use `TPS Health: Log food (tps-health:log-food)`. Native-plus ownership stops at the nearest Base embed or Home component, so one view can never execute a neighboring view's command override.
- Row context menus are record-aware: right-clicking a TPS Table row selects that source line, always exposes a list-safe Tags submenu, uses constrained Kind/entity/selector pickers, supports exact-member list add/remove, validates numbers, routes datetime and snooze values through date-aware controls, renders clearable booleans as native checkboxes, and opens the recurrence modal for task-line recurrence. Configured Folder cells show the containing note's folder and formula/source fields remain read-only. The menu can open or delete the exact source line. Food rows are handed to TPS Health when its API is available, so serving edits use TPS Health's serving-adjust flow and recalculate qty/amount/macros together instead of raw field editing; that Health-owned menu is outside GCM's generic record actions.
- Shift-click selects an inclusive range in the table's current rendered order without opening a record; Cmd/Ctrl-click toggles one row. Plain clicks still select and open the record, and modifier-clicking a configured filename link delegates to row selection. Only task-shaped rows form a multi-row mutation batch, and the shared task context menu receives only selected rows whose exact revisions still exist. Bullets, headings, generic records, and mixed selections remain scoped to the clicked row. Every rerender intersects selection with the current rendered task rows so a removed, replaced, or reclassified row cannot transfer selection to another record.
- Task-shaped TPS Table rows carry exact path/line identity. Clicking their task content opens the shared virtual task card for quick text, tag, and inline-property editing; clicking the configured filename link remains a full-note action and participates in Hover Editor-on-click when that setting is enabled.
- The TPS Table header is rendered as a normal opaque table header instead of a sticky overlay, preventing the first data row from painting underneath column labels in embedded scroll containers.
- TPS Table columns use persisted pixel widths and resize handles on header dividers. When the total column width exceeds the Base panel, the table uses its native horizontal scrollbar instead of compressing every column into the visible area; long result sets use the same element's native vertical scrolling. GCM does not capture wheel, pointer, or transform gestures for table panning, and safe rerenders restore both scroll axes within the new bounds.
- Top-level Base formulas are available to every synthesized row as `formula.<name>`. TPS Table uses typed formula results for filters, columns, sorting, multi-value grouping, and numeric totals. Bare properties resolve from the line row before containing-note frontmatter; `note.*` remains source-note-only, `file.*` describes that source file, and `line.number` is one-based. For formulas, `row.kind`/`row.itemKind`/`row.itemType` remain the structural row kind, `row.explicitKind` is the line's configured explicit identity, and `row.kinds` is the additive deduplicated list of both; use `row.kinds.contains("task")` for additive identity tests. Formula columns and defaults are read-only. A formula-dependent create checks the exact candidate line inside `Vault.process`; stale placement or any unresolved result prevents the append.
- TPS Table classifies the complete Markdown document before testing any line filter or formula. YAML frontmatter and fenced, indented, HTML, or comment blocks cannot become synthesized task, bullet, heading, or generic-property rows, while physical source line numbers remain exact.
- TPS Table's revision-keyed document cache reuses parsed eligible lines across unchanged rerenders, invalidates on authoritative file changes, cancels superseded scans, and bounds a cold refresh to eight concurrent Markdown reads. The visible table remains ordinary DOM with native scrolling rather than a virtualized renderer.

- Within task rows, `tag`, `tags`, `task.tag`, and `task.tags` are equivalent and combine raw `#tags` with singular `[tag:: …]` and plural `[tags:: …]` fields. Prefixes and a leading `#` are optional, comparisons use exact tag membership, and `file.tags` remains the separate containing-note namespace.
- TPS List's structural row kinds are `note`, `task`, `bullet`, and exact heading levels `h1` through `h6`; `header` and `heading` are generic aliases for every heading level. Bare `kind` filtering is intentionally additive: it combines that structural identity with the configured explicit Kind property, so `kind == task` returns checkbox rows plus notes whose property is `kind: task`, and a checkbox carrying `[kind:: project]` matches both `task` and `project`. Use `itemKind`/`itemType` (or their `tps.*`/`kanban.*` aliases) when only structural shape should match; use `note.kind` when only a native note property should match. A heading row also exposes `heading.level`, `heading.text`, `heading.line`, and `heading.path`; common synthesized-line aliases include `line.text`, `line.number`, and `line.path`.
- When bare Kind or a configured Folder field participates in a note filter, TPS List narrowly reconciles Obsidian's native note result against GCM's additive Kind and source-folder contracts. It can restore a conclusively matching missing note or remove a conclusive stale-folder false positive, but never recreates notes during active native search and never guesses through unsupported context or predicates. Results are cached by filter, folder configuration, native paths, and reconciliation revision.
- TPS List can group synthesized task, bullet, and heading rows by their containing note. Choose `file.name` for filename groups or `file.path` for unique vault-relative note groups; the same source-note aliases supported by TPS Table resolve from each row's actual source file. Configured Folder fields use that same current source folder rather than a stale inline/frontmatter carrier. Typed multi-value groups use the per-view **Items with multiple values** setting, defaulting to one row in every matching lane; combined mode uses one deterministic group. Source-note and Folder groups are read-only, so dragging a row cannot write a `file.*`, path, or Folder alias into Markdown metadata.
- Task rows preserve their Markdown parent/child hierarchy within each displayed Base group. Base sorting applies to roots and siblings, but matching descendants stay directly below their matching parent at the correct visual depth. If the direct parent is filtered out or placed in another group, the child renders as a root row.
- Shift-click selects the inclusive visible range across notes, checkbox tasks, plain bullets, and headings, even when the endpoints are different row kinds or the same source record appears in more than one group. Cmd/Ctrl-click toggles individual rows. Selected note rows continue to use Obsidian's multi-file menu, selected checkbox tasks use GCM's batch-safe task menu, bullet menus remain scoped to one line, and heading rows open their exact source line without entering task mutation flows. Each rerender intersects the selection and anchor with current occurrence identities, preventing a deleted or relocated row from donating selection to a replacement.
- Task rows support native pointer drag between writable groups. Desktop activates on pointer movement; touch waits 550 ms and cancels when movement exceeds 10 px before activation, preserving ordinary vertical scrolling. Pointer capture, hover state, timers, and document listeners are cleared on drop, cancel, lost capture, rerender, and unload. The drop carries the rendered raw line, re-resolves it uniquely at commit, and refuses stale or duplicate revisions.
- Right-click Tags are Base-owned and do not depend on the global custom-property menu switch. Note rows edit frontmatter `tags`, checkbox tasks edit inline Markdown `#tags`, and plain bullets expose a scoped `Line tags` submenu with guarded exact-line add/remove writes. If configured note properties are also visible, line and note tag actions remain separately labeled.
- Clicking a TPS List task title opens the shared virtual task card instead of navigating away. The card shows editable task text and visible `#tags` but omits inline `[property:: value]` fields and hidden TPS payload carriers. Save reattaches metadata from the current exact source line, unchanged saves are byte-preserving, and the card offers Save, Cancel, and Open in note. Clicking a note row or a task's configured filename link continues to target the full note and uses Hover Editor-on-click when `Force previews for Base links` is enabled.
- Configured list, tag, and link/entity properties aggregate every repeated exact-key carrier before display or edit. Membership filters and removal compare canonical list members rather than substrings; successful line edits or lane drops preserve unrelated members and rewrite only the edited property to one balanced carrier. Text, number, selector/Kind, checkbox, datetime, snooze, and task-line recurrence editors use their typed controls. Folder and formula values are read-only. Whole-note recurrence displays its value or **Not recurring** as a read-only cell so a direct frontmatter change cannot accidentally impersonate the canonical series/template lifecycle.
- TPS List keeps Obsidian's native formula values for real note `BasesEntry` rows and evaluates the same Base definitions for synthesized tasks, bullets, and headings. Formula properties can drive display, direct or structured filters, search, sorting across mixed native/synthetic rows, and scalar or multi-value lanes. `row.status` preserves an inline relational Status value, while `task.status` is the checkbox-workflow state. `row.kind` remains structural for compatibility, `row.explicitKind` carries only explicit identity, and `row.kinds` is their additive list. Formula properties cannot be edited or used as writable drag/default targets; task creation validates formula filters against the exact prospective line and note creation with an unverifiable formula predicate is refused.
- Configured checkbox/boolean properties render as native controls on both note and synthesized-line rows. Native Obsidian `BooleanValue` wrappers are read through the public Value contract; frontmatter stores real booleans, while line metadata stores lowercase inline `true`/`false`. The visible states are **Yes**, **No**, **Not set**, and **Invalid**, and a failed or stale write restores the prior control state.
- Notes, tasks, bullets, and headings share one two-column row contract: a decorative file/list/heading marker or the real task checkbox occupies the same leading slot, and title plus properties wrap in the body column. The collection retains list semantics, decorative markers are hidden from assistive technology, only task rows expose a leading workflow checkbox, and nested task depth uses logical inline padding rather than a file-row indentation workaround.
- Each source note is document-classified and task-parsed once per cold load. TPS List excludes YAML frontmatter and fenced, indented, HTML, or comment blocks before hierarchy, filtering, formulas, previews, or overflow counts; protected top-level blocks also break stale list ancestry instead of attaching a later row to an earlier parent.

## TPS Notebook Navigator File and Note Row Menus

- GCM registers its canonical whole-file actions with TPS Notebook Navigator through Navigator's public lifecycle-safe `menus.registerFileMenu(...)` API. Normal files, Recent files, shortcuts, Notes, and every other file-backed Type therefore use one GCM-owned configuration and mutation implementation. GCM also retains the older `menus.registerRowMenu(...)` note-entity bridge for structurally compatible Navigator hosts. Registration is load-order independent, replaced when Navigator reloads, refreshed when GCM's menu visibility setting changes, and disposed on either plugin's unload; GCM never inspects Navigator through Obsidian's private plugin registry.
- Navigator continues to own its native Title/Rename, Tags, Style, Move, Duplicate, and Delete actions. When every selected file is Markdown, GCM omits only its standard `tag`/`tags` property to avoid duplicating Navigator's native Tags action; custom tag-list fields such as Categories remain available, and non-Markdown selections keep all applicable configured fields. For a single selection GCM contributes applicable configured custom properties, relational actions, attachment embedding, note conversions, optional time tracking, PDF writing, and Archive/Unarchive. Multi-selection keeps only actions valid for the complete batch, so a command never silently mutates the first selected file or a compatible subset. Task, checkbox, bullet, heading, and third-party provider rows remain owned by their exact-line menus.

GCM does not consult the active editor, File Explorer selection, or another ambient selection for this route. - Menu construction is synchronous and buffered: Navigator receives GCM items only after the canonical builder completes successfully. A candidate API replacement must install both supported registrations before the prior host is released. **Inline menu only** suppresses both integrations, and the bridge adds no persisted setting or note-data migration.

### Synthetic Base formula contract

`plugin.api.formulas` is version 1. It compiles one authoritative `formulas:` map, creates isolated memoized row sessions, evaluates declared formulas or filter expressions, and exposes shared format/comparison/sort/group/truthiness adapters. TPS consumers must require the exact API version when formulas are configured; ordinary Bases without formulas continue without that dependency. GCM emits `tps:gcm-api-changed` with the exact source identity, API object, availability, and formula, line-metadata, Entity Index, configuration, task-line, checkbox, Task API, and item-history capability versions—including `tasksVersion: 3` and `itemHistoryVersion: 1` while available and `null` on removal. Consumers register before sending `tps:gcm-api-request`, replace their cached object on every compatible available payload, and clear it on unload; polling and private plugin-registry discovery are not part of this contract.

`plugin.api.lineMetadata` is also version 1 and read-only. `scanDocument(content)` classifies full Markdown block context and returns a frozen array of frozen eligible physical-line records `{ index, lineNumber, text, start, end }`; index is zero-based, line number is one-based, and offsets address the original UTF-16 source without newline normalization. It excludes YAML frontmatter and CommonMark fenced, indented, HTML, and comment blocks. `parseLine(line)` then performs one reusable semantic scan and returns `{ fields, tags, displayTitle }` for an admitted checkbox task, bullet, or heading; the narrower `readInlineFields`, `readInlineFieldValue`, `readTags`, `getDisplayTitle`, `parseStringList`, and `parseTags` functions use the same canonical rules. A missing field returns `null`, while a persisted blank field returns `""`. Inline-field parsing preserves nested wikilinks and comma-bearing aliases; list parsing supports scalar, comma-separated, and balanced `[a, b]` storage without splitting wikilink commas; visible titles unwrap links and Markdown presentation; closed inline code and protected TPS metadata carriers cannot masquerade as properties. Synthetic-line consumers require the document scanner and exact parser contract and fail closed when either is missing, throws, or returns malformed coordinates; they do not fall back to copied regex parsing.

Persisted inline line properties remain strings because Markdown does not carry the authoritative Base property schema needed for safe implicit coercion. Formula authors must request the intended interpretation explicitly—for example `number(points)`, `date(scheduled)`, `allDay == "true"`, `labels.split(",")`, or `link(owner)`. The documented Bases `list(value)` behavior still wraps one scalar and does not parse comma/bracket syntax. GCM does not guess that a string is a number, date, boolean, list, or link merely because it resembles one.

Additional version-1 capabilities keep cross-plugin behavior explicit. `configuration.isInlinePropertyAllowed(key)` and `configuration.getParentLinkPolicy()` expose only supported decisions rather than the settings object. `services.parents.getParentKeys()` and `getChildKeys()` expose normalized relationship field aliases; `services.status.getStatusPropertyKey()` and `getRelationalStatusPropertyKey()` distinguish checkbox-owned workflow storage from an entity-backed Status relation. `taskLines.handleContextMenu()` and `taskLines.openQuickEditorForElement()` own task-line UI routing. `taskCheckboxes.getMappings()`, `stateForStatus()`, and `statusForState()` return the exact ordered runtime mapping without supplementing missing rows or leaking mutable settings. `tasks.setCompletion(ref, completed)` is the high-level binary checkbox mutation: it resolves GCM's configured complete/todo state, preserves exact task-line and live-mapping guards, returns the refreshed exact-line task record, and invokes the same recurrence, final-note-status, and checklist-property follow-up used by GCM's own UI. Mapping-aware classification keeps configured nonterminal states open, configured terminal states complete, and migrated Daily Note scratchpad records outside both categories. `tasks.setCheckbox(ref, checkbox)` remains the lower-level marker mutation, but the requested marker must still be owned by the live mapping at commit time; unowned structural markers are readable but not writable through the API. Consumers fail closed when a required capability or exact version is unavailable.

The supported deterministic subset covers arithmetic/comparison/boolean expressions; lazy `if`; formula dependencies; literals; note/file/row namespaces; date and duration arithmetic; string, number, list, object, and regular-expression methods; and local link/file metadata already supplied in the row context. To avoid pretending that an unavailable result is reliable, synthetic rows explicitly reject `random()`, `file()`, `html()`, `image()`, `icon()`, `file.backlinks`, `file.embeds`, and link target resolution through `asFile()`/`linksTo()`. Moment-compatible date formatting currently supports the documented common year/month/day/weekday/time tokens rather than every Moment token. There is no `eval`, `Function`, private Bases API, host monkeypatch, temporary-note evaluation, or same-name property fallback.

## TPS Home View

- `Open TPS Home` opens a rendered Obsidian `ItemView` with view type `tps-home`; it is not backed by a Markdown file.
- Daily Notes have a date-backed Home presentation. When a Daily Note enters Reading View, GCM replaces that Markdown view in the same tab with `tps-home` state carrying the real Daily Note path and ISO date. Previous, Today, and Next create or reuse the corresponding configured Daily Note and navigate the same Home tab to it, so every dashboard date has a canonical file and Base context. The header file-edit action restores that exact Daily Note as Markdown Live Preview; switching it back to Reading View restores Home. Notebook Navigator Shift/multi-select and drag gestures are selection-only exceptions: the exact leaf/path remains Markdown across recurring Home scans until the leaf changes file or that note receives a later unmodified Navigator click. Existing view-mode rules remain authoritative about which Daily Notes default to Reading versus Live Preview.
- The Home view is a dashboard/editing surface over source notes and synthesized source lines. Clicking a row opens the source item rather than editing the Home surface itself.
- Home dashboard components are reusable `.base` embeds or command-triggered workflows. Header actions are layout configuration stored separately from Base query definitions, so the same Base remains usable on its own and Home does not hardcode domain buttons.
- Home is date-scoped. Previous/today/next switch the canonical Daily Note backing the dashboard. Embedded Bases receive both the selected date context and that Daily Note as their render source, so `this.file.path` resolves to the selected day while whole-base and active-view filters retain normal ordered AND composition.
- On mobile, the Home date/navigation controls float above the dashboard content and automatically hide while scrolling down/swiping up, then reappear when scrolling back up.
- The default capture surface is `Daily Note Feed.base`, a TPS List Base whose whole-base filters scope displayed rows with `file.path == this.file.path` and provide the explicit creation sink `task.path == this.file.path`; its view filter can combine task, bullet, and heading rows. `kind == header`/`heading` includes every Markdown heading and creates H1, while `kind == h1` through `h6` targets and creates one exact level. Its explicit `createAction: default` sends pointer, touch, Enter, and Space activation through TPS List's ordered filter-derived creation; the first branch that satisfies the rest of the effective query owns the new line.
- `Capture: Today's Daily Note`, `Capture: Current note`, and `Home: Capture to selected Daily Note` open the same focused native capture modal. The Home command retains its explicit selected-day target, while the other commands resolve today's configured Daily Note or the active Markdown note respectively. The editor auto-sizes to its typed lines, never owns an internal vertical scroller, and the entire input shell focuses it on pointer/touch. Each contentful top-level submitted line receives the same hidden `createdDate` value inside its `tps-inline-props` carrier; indented descendants stay nested without an independent timestamp. The command modal and embedded/mobile formatter share that root-versus-descendant rule.
- Existing destination notes with Markdown headings expose an optional `Place under` selector with `Note body` plus every H1-H6 section in document order. Duplicate same-level headings are numbered. Heading discovery skips YAML frontmatter and fenced code; the chosen identity is re-resolved inside the atomic write, section ownership includes lower-level nested headings, and a stale or ambiguous choice is refused without changing the note.
- `HomeCaptureService` owns Daily Note resolution, current-note validation, bullet/task formatting, section selection, and atomic `vault.process` writes. Today/selected-day capture resolves the canonical template-aware Daily Note first; a missing or failed configured template surfaces an unavailable-note state and no capture is appended. Contextual Home capture validates the exact target path and fails closed if that file disappeared; it never infers the target from the active workspace file.
- The default Home layout is Daily Note Feed, Calendar, and Open unscheduled tasks. Food and Activity components remain available for an explicit user-added layout. Legacy `quick-capture` settings migrate to the feed Base.
- TPS Finances is intentionally paused and has no Home component, Base embed, normalization rule, or add-component entry. Its standalone plugin and stored finance data remain untouched so development can resume later without a Home dependency.
- Layout edits are locked by default. Click the Home edit button to reveal component add/move/remove controls and each built-in card's **Choose Base** / **Change Base** action, then click done to return to the normal use surface. A successful Base choice preserves Home scroll and returns focus to the rebuilt card without a timer. Phone edit controls wrap the readable Base action above 40-pixel layout controls. Home components opt out of the file-level right-click menu, so embedded Base panels do not expose Archive/Delete as a way to remove dashboard components.
- Right-clicking the header or unused surface of any Base-backed Home component opens a focused menu with `Open Base`. The Base opens in its own tab so Home remains available. Task, note, heading, bullet, table-record, and calendar-item right-click handlers keep ownership of their existing item menus.
- Home edit mode exposes a `+` action control on every component header. The searchable picker can add any command; configured actions can be reordered, replaced, removed, or switched between `Target selected Daily Note` and explicit `Run normally in workspace`. Selected-note is the safe default.
- Calendar renders exactly the configured `.base` through TPS Calendar Base's embed API when available; `home-schedule.base` remains the backward-compatible default. A missing configured file is shown as unavailable instead of falling through to Calendar Base's sidebar setting or `scheduled.base`. Calendar navigation and create controls are owned by the embedded Calendar view rather than duplicated in the Home panel header. Home navigates the embed to the selected dashboard day, lets Calendar apply its responsive one-, two-, or three-day width behavior, and scrolls to the current time only when the selected day is today. The supported native Markdown/Base embed path remains available when the Calendar plugin API is unavailable.

Home asks TPS Health to create/repair a missing Base only when that canonical default is still configured; a missing custom selection fails visibly instead of being replaced. Food totals are ordinary TPS Table view configuration rather than Home-specific UI; the default Food Log view uses `totalsRow: top`. Its `Log food` header action is ordinary `homeComponentActions` configuration and routes the selected Daily Note/date through TPS Health’s contextual provider.

## Mobile Header Persistence

### Mobile overlay and input contract

- TPS-owned anchored cards use the shared `KeyboardAwareOverlay` utility and `.tps-keyboard-aware-overlay` class. The utility intersects `window.visualViewport` with the layout viewport and Obsidian Mobile's native Capacitor keyboard height, clamps the card to the smallest reported usable area, uses a compact bottom-sheet placement on phone-sized surfaces, and repositions throughout the keyboard animation. Native keyboard events cover the iOS overlay mode where neither viewport changes; viewport intersection still handles either browser API lagging.
- TPS-owned Obsidian modals use the shared `mod-tps-gcm` class. The plugin publishes visible-viewport CSS variables and the shared modal rules keep inputs and scrollable content inside the portion of the screen above the mobile keyboard. Mobile text controls retain a 16px minimum font size to avoid iOS focus zoom.
- New editable popups must use the shared overlay utility rather than adding their own `visualViewport` listeners. New input modals must add `mod-tps-gcm`; custom modal classes may extend the appearance but must not replace the shared viewport rules.
- The task quick editor and editable Base note preview are the first anchored surfaces migrated to this contract. All current GCM `Modal` subclasses now opt into the modal contract.
- Other TPS plugins opt in with `tps-keyboard-aware-modal`. GCM publishes the visible-viewport variables and shared mobile modal rules globally so Calendar, Controller, Kanban, Finances, Health, and Messager do not each maintain keyboard geometry.

- Mobile swipe/gesture collapse is intended to hide floating controls, including the persistent action bar, inline hovering property strips, daily-note bottom navigation, base preview property overlays, the `Show completed`/`Show tasks` reveal widget, and any future TPS-imposed hover element marked with `.tps-gcm-hover-element` or `data-tps-hover-element="true"`.
- External parent-nav actions are rendered with stable plugin/action data attributes. Invisible external actions are `display: none` while resolving and are removed when their visibility callback returns false, so mobile bottom navigation does not reserve empty rounded slots for unavailable actions.
- Mobile bottom navigation renders external integration actions even when the full parent-nav placement is configured for the top/desktop note chrome.
- On phone layouts with property chips, external integration actions are injected directly into the mobile action bar next to native actions instead of the hidden bottom parent-nav row.
- Persistent note header content remains visible while scrolling: title icons and GCM-rendered stacked properties under the title are not hidden by keyboard or gesture-collapse state.
- Normal note scrolling on mobile is native-first. Floating menu collapse listens only to passive scroll movement with mobile-specific hysteresis; it does not attach `touchmove` gesture handlers to the Markdown scroller, so finger scrolling is not intercepted by GCM chrome.
- Stacked properties remain visible while editing on mobile; keyboard suppression only hides floating/hovering chrome and top navigation wrappers that do not contain stacked properties.
- Keyboard suppression still hides floating menu surfaces so editable fields are not covered by action bars or popovers.
- The hidden task reveal button remains mounted while editing; the quiet edit window prevents unnecessary remounting but does not suppress the button.
- Mobile reading mode is treated as a first-class rendered surface, including `.markdown-reading-view`, so hidden task lines get the same fixed reveal button and tap handling as preview/rendered views.
- `Persist task reveal state to frontmatter` is off by default. When enabled, `Show completed` and `Show tasks` write note-level state to the configured `gcmTaskVisibility` frontmatter property instead of using only temporary per-view reveal state.
- `gcmTaskVisibility.showCompleted` stores the completed-task reveal state, and `gcmTaskVisibility.showTasks` stores the reading-mode all-task reveal state. When the setting is disabled, no frontmatter is written and the reveal buttons keep their temporary/resetting behavior.
- Inline and stacked property tag chips render only note-level frontmatter tags from `tags` / `tag`; body hashtags and task-line hashtags remain searchable content but are not shown as note property values.
- Custom property visibility is key-aware:
  - `Always show`: render regardless of frontmatter.
  - `Only when key has value`: render only when the key exists and is non-empty.
  - `Only when key exists`: render when the key exists, even if its value is empty.
  - `Only when key exists but is empty`: render only when the key exists and has no value.
  - `Only when key is missing`: render only when the key does not exist.
  - `Only when missing or empty`: legacy empty behavior; render when there is no populated value.
  - `Never show`: hide the configured property even when the note has a key and value.
- `Inline visibility` and `Context menu visibility` can override the default property visibility independently. For example, a property can use `Inline visibility: Only when key exists` and `Context menu visibility: Always show`, so missing keys stay out of the inline chip row but remain available from right-click actions. A rendered property row's visibility menu edits only the inline override, exposes **Use property visibility** to inherit the default again, and refreshes all mounted GCM Properties panels immediately without changing frontmatter.
- Property row context menus include `Remove property from file`, which deletes that frontmatter key from the current file without removing the reusable property definition or changing its visibility settings.
- Right-click edits of rendered inline properties use an atomic exact-line revision check. Unrelated concurrent note edits are preserved; a source line that moved is updated only when its original text has one unique match, while missing or ambiguous revisions are refused rather than writing to the wrong line. Existing CRLF or mixed line separators are retained.
- TPS Health owns its food/workout property definitions and domain surfaces. GCM does not bundle those definitions into its core custom-property catalog or recreate them during settings load. Retiring the old catalog entries changes plugin configuration only; Health frontmatter and inline fields already stored in notes are preserved. Generic Health-aware row rendering remains available where a dedicated Health view supplies the data.
- Completing a note from outside GCM-owned controls is watched through vault/metadata events. If a note status transitions into `complete`/`completed`/`done` from native Properties, Bases, Kanban, calendar/reminder surfaces, or another plugin, GCM runs the same open-checklist guard and reverts the status if the prompt is canceled.
- The external completion guard is user-facing and is not suppressed by the mobile/background-automation gate, so iPad and mobile completion actions still prompt when a note has open checklist items.
- GCM defines a shared workflow/run frontmatter contract for process-style records. `workflow` is the reusable template/definition, `run` is one completable single-session instance, and `log` is available as the generic record kind for log-style domains. Run/workflow subtype strings remain open to domain-specific values while retaining the known `workflow` and `workout` literals. TPS Home's in-memory contextual Workout Base filter accepts canonical `runKind: run` plus `runType: workout`/`workflowType: workout` records as well as legacy `kind: workout` notes. Existing Health-provided Base filters are preserved. `recurrenceMode: completion-triggered` means the next instance is generated from completion flow rather than a date scheduler. Template propagation intentionally skips run-instance fields such as `startedAt`, `endedAt`, `completedDate`, `durationSeconds`, `previousCompletedDate`, `secondsSincePreviousCompletion`, `lastCompletedDate`, `lastSessionPath`, and `nextEligibleDate`.

## Native properties for non-Markdown files

- GCM owns one native property system for every non-Markdown vault file, including Canvas, Base, PDF, image, audio, video, and arbitrary asset types. It has no runtime dependency on Advanced Canvas and never writes property data into Canvas JSON or any other source-file bytes.
- Properties live in an ordinary Markdown companion under `_assets/TPS File Properties/<source path>.md`. Unsafe, overlong, or occupied mirrored paths use `_assets/TPS File Properties/_by-id/<file ID>.md`; GCM never overwrites a collision. Companions are created lazily by an explicit property edit or **Create file properties note**, not by a startup scan.
- Companion frontmatter reserves `tpsGcmFileProperties`, `tpsGcmFileId`, `tpsGcmSource`, `tpsGcmSourcePath`, `tpsGcmSourceExtension`, `tpsGcmSourceMissing`, `tpsGcmTombstonedAt`, `tpsGcmPendingTargetPath`, `tpsGcmNeedsMerge`, and `tpsGcmImportedCanvasAt`. Every other frontmatter key is an ordinary user property that Obsidian Properties and Bases can index and edit directly.
- GCM menus, configured property rows, badges, bulk edits, Vault Query, Notebook Navigator rules, and the public `fileProperties` v1 API resolve a non-Markdown target through the same store. Non-Markdown parents and children also read and write these logical properties, including the configured exact key/value ignore rule. The entire managed root is reserved: files inside it cannot become property sources, and valid companion records remain excluded from GCM task, recurrence, parent/child, linked-context, entity, Daily Note, title, identity, picker, and background-note workflows even if moved elsewhere.
- A native Obsidian Base sees the Markdown companion as its property-bearing row. To expose active records only, require `tpsGcmFileProperties == 1`, exclude `tpsGcmSourceMissing == true`, and exclude nonempty `tpsGcmTombstonedAt`; put `tpsGcmSource` first so the logical asset is easy to open. Native `file.*` values and the file-name column still describe/open the companion. GCM's TPS List maps that row back to the logical source for file name, folder, extension, hierarchy, selection, opening, context menus, sorting, and editing; an unfiltered source-plus-companion result is deduplicated in favor of the companion at its configured position.
- File and folder renames update the reserved source mapping before any best-effort companion move, so a sync or path collision cannot strand otherwise valid properties. Deleting a source removes its live `tpsGcmSource` link and retains the companion with `tpsGcmSourceMissing: true`; a later file that reuses the path cannot read or mutate that history. **Relink** explicitly attaches one unique retained record to a live non-Markdown target. For an exact-path replacement, **Start fresh** adds `tpsGcmTombstonedAt` to the retained identity and creates an independent file ID. Duplicate source mappings, duplicate IDs, and occupied companion paths fail closed instead of merging or overwriting.
- Changing a source from non-Markdown to Markdown never injects companion values into the Markdown frontmatter automatically. GCM retains the old identity as missing, sets `tpsGcmPendingTargetPath` and `tpsGcmNeedsMerge`, and exposes the pending target in the relink picker. Merging into the Markdown target requires a future explicit merge workflow; relinking the retained record to another non-Markdown file uses that file instead.
- Existing Canvas `metadata.frontmatter` remains read-only legacy input. **Import legacy Canvas properties** performs an explicit copy migration, and the first GCM property mutation of an unmigrated Canvas lazily copies legacy values before applying the edit. `tpsGcmImportedCanvasAt` records that copy. The original Canvas JSON is never cleaned up or synchronized back automatically.
- Public integrations use the additive `fileProperties` v1 surface; the deprecated `canvasProperties` API remains a compatibility alias backed by the same generic store. Public mutations with no valid cause are classified as `{ kind: "automation", sourcePluginId: "tps-global-context-menu", surface: "plugin-api" }`; callers may pass an explicit `user` or `automation` cause. GCM-owned direct actions use a user cause.
- Every committed change emits general file invalidation plus a redacted `tps:gcm-file-properties-updated` payload containing the source/property-file paths, stable file ID, action, changed key names, timestamp, source plugin, and optional surface—never property values. User causes also emit the explicit-action signal; automation causes do not. Direct YAML edits refresh GCM consumers, while companion deletion emits a redacted removal invalidation and never recreates the file.
- Item History v1 deliberately remains task-only. Asset-property history is a future v2 surface keyed by stable `tpsGcmFileId`; this release does not record asset changes in the task journal. TPS Notebook Navigator's GCM rule automation can consume companion properties, but the Navigator's own native rows, search, and property tree do not yet project them.

## Task-Line Context Menus

- GCM owns context-menu actions for rendered task rows from Kanban and Calendar surfaces.
- Task menu titles are presentation-only plain text: local wikilinks and Markdown links are unwrapped to their labels, never rendered as link markup in the menu, while legacy leading local links are migrated to hidden `associatedNotePath` metadata when a task is edited. An existing association changes the action label to `Open linked note`; otherwise it remains `Create note for task`.
- The first task action is `Title: <plain task name>` and opens a `Task title` editor. It rewrites only the safely re-resolved checkbox line; it never calls the note-level title action or renames the associated note. Editing a legacy leading title link converts the visible task text to a plain label while preserving the note relationship in hidden `associatedNotePath` metadata.
- TPS List headings and bullets plus TPS Table records use the same title-row contract. Their editor changes the clicked line item rather than its containing/source note; a leading wikilink or Markdown link keeps its target and receives the new display alias. The composed file menu suppresses its note title row on those line-item surfaces, preventing two competing title actions.
- Checkbox/status choices come from the configured linked-subitem mappings. Optional property rows obey the global `Show custom properties in context menu` switch plus each property's context visibility, scope, exclusion, and disabled/hidden rules. **Allow `@@` inline set** applies only to the `@@` insertion workflow and does not hide a property that is explicitly configured for a right-click menu. Generic date fields use a date-only editor; only `scheduled` exposes all-day, time-estimate, and computed-end controls. Invalid numeric values are refused rather than writing `NaN`.
- Single task rows in TPS List and task-shaped TPS Table records always include a Tags submenu even when optional custom-property rows are disabled. It adds/removes inline Markdown `#tags` through the same stale-target-safe task mutation path and suppresses the configured Tags property on that menu to avoid duplicate actions. Add-tag fields accept comma- or whitespace-separated values, normalize and deduplicate the complete entry, and commit the resulting tag set in one guarded line update; note-level GCM tag actions use the same multi-value input contract.
- The lower task-action section begins with `Move task from <source note>...`. The source label uses the note's canonical display title so embedded Calendar, Kanban, TPS List, and TPS Table tasks identify their actual containing note before the destination picker opens.
- Every mutating task action re-resolves the current source line by exact raw text, stable `tpsId`/`subitemId`, or one unique plain title. Callers may require the stricter exact-or-identity route when even a unique title fallback is unsafe. Ambiguous or stale targets fail closed instead of changing the first match. Timer identity writes, recurrence-template edits, Task API updates/deletes, checkbox changes, drag/move/delete operations, and note associations emit concise route/result diagnostics. Async modal actions report rejected writes rather than failing silently.
- Task-line settings are grouped under `Workflows > Tasks`, including the shared TPS List/Table fallback write note, Daily Note move-source behavior, local item-history recording/retention, task hiding/reveal behavior, task status-to-checkbox reconciliation, linked child-note checkbox rows, checklist completion warnings, and checklist promotion behavior.
- `Completion prompt status options` are offered after the last open checkbox is resolved only when the containing note already has a populated frontmatter `status`. Missing, null, empty, and whitespace-only status values do not create a status or open the chooser; populated non-final statuses retain the configured prompt.
- `Task hiding exclusions` defaults to no exclusions. Matching files, folders, tags, and cssclasses bypass completed-task hiding, reading-mode all-task hiding, and reveal buttons; patterns support exact paths, folder prefixes, wildcards, `name:<basename>`, `re:<regex>`, `#tag`, `tag:<tag>`, `cssclass:<class>`, and `class:<class>`. `Inbox/` and `#tps/workout` are example/local vault configurations, not product defaults.
- Long-pressing an inline task checkbox keeps the checkbox-state choices first, then appends GCM task-line actions such as title editing, inline property edits, opening the task line, moving the task to another file, deleting the task, and time tracking.
- The virtual task quick editor shows a native Obsidian task checkbox inline beside the task content. Tapping it toggles between open and complete; long-pressing it (or right-clicking on desktop) opens the configured checkbox/status choices. Non-complete custom markers use the native mixed state. `Bullet — No status` removes the checkbox plus inline status/completion metadata and closes the task editor because the resulting line is a normal bullet, not a task.
- Task quick editing is target-owned rather than proximity-based. GCM opens it only from the task title/body on supported task surfaces; Base property controls, menus, suggestions, popovers, and modals are hard interaction boundaries and can never resolve a task hidden underneath them.
- Reading-mode task rows resolve source lines from rendered `data-line` metadata as zero-based candidates and validate the candidate against the clicked row text before opening the menu, so repeated checklist rows do not default to the first task.
- Task-line context menus apply a temporary active-line highlight in reading mode and Live Preview while the menu is open. Highlights are scoped to editor lines, rendered task list items, and explicit TPS Calendar/Kanban task row elements so broad note/list wrappers are never painted. Cmd/Ctrl-click toggles task-line selection within the current note; right-clicking a selected task exposes batch-safe actions for selected tasks, including status changes, adding a tag, moving to a note, delete, and clearing selection. Single-task modal actions remain single-task only.
- When a rendered card's stored line number is stale, GCM falls back by matching clean task-title variants instead of the full rendered metadata string, so chips like scheduled date, status, time, and all-day flags do not prevent resolving the source checklist line.
- GCM context-menu moves, task drag-and-drop, and API consumers use one Task API v3 transaction. GCM-owned context-menu and drag routes request `configured-daily-note`: the default **Keep a migrated marker** policy preserves the Daily Note as a scratchpad/inbox record with `[>]` and `[migratedTo:: [[Target]]]`, while **Remove the source block** deletes the complete source block after the destination is confirmed. Migrated records participate in the completed-task hiding scope alongside complete and won't-do tasks; otherwise they remain visible in Reading View and Live Preview. Non-Daily-Note moves remove the source. Public Task API callers that omit `sourcePolicy` retain the legacy remove-source default; explicit `remove` and `migrate-if-daily-note` requests are unchanged.
- Cross-note moves write the destination first, require the complete current nested source block to remain byte-identical, and mutate the source only after revalidation. Exact before/expected snapshots distinguish a rejected-but-committed write from an unchanged or conflicting write; rollback restores only the exact inserted destination snapshot. Conflicts preserve data and return `ok: false, changed: true` instead of pretending nothing happened. Timer duplicates, recurrence instances/templates, and migrated Daily Note scratchpad records remove cloned stable/external/association identities so the destination or recurrence chain remains authoritative.
- GCM-created task lines add inline created/modified timestamp fields using the configured `dateCreatedFrontmatterKey`, `dateModifiedFrontmatterKey`, and `fileTimestampFormat` settings. GCM task-line mutations update the configured modified timestamp, while task completion still adds or removes inline `completedDate` based on the checkbox/completion marker.
- Task status-to-checkbox reconciliation derives completion markers from the linked checkbox mappings. Default `complete` and `wont-do` mappings therefore preserve or add inline `completedDate` when statuses become `[x]` or `[-]`, and non-completion mappings remove stale completion dates.
- Reserved TPS inline metadata such as `tpsId`, `subitemId`, `tpsInlineProps`, and `tps-inline-props` is hidden in Live Preview, Reading View, TPS Home's Daily Note preview, and other rendered Markdown hosts. Strict Source mode still exposes the raw Markdown for inspection. Visible task chips are limited to configured user-facing inline properties.
- Removed settings: subitem path/status/priority defaults, new-subitem visual metadata seeding, Bases icon helper-field writes, and native Properties-under-title rendering. New subitem notes default to the parent note folder, or vault root when there is no parent folder, and no longer receive default status/priority solely from removed settings. Normal icon/color rule fields still write through Notebook Navigator rules.
- Settings normalization: child-status checkbox mappings now preserve default icon/label metadata when edited through the textarea setting, empty/invalid parent body-link format values normalize back to `wikilink`, legacy top-level Notebook Navigator smart-sort payloads are migrated into the nested canonical `notebookNavigatorRules.smartSort.buckets` shape on load/save, Notebook Navigator icon/color rule filtering now matches exact case-insensitive field values such as `working`, and Daily Notes / Recurrence child settings collapse immediately when their parent feature toggle is disabled.
- `Collapse headings on first open` optionally runs Obsidian fold-all when a Markdown note is newly opened on desktop. It is intentionally skipped on mobile so Obsidian's native heading/list collapse controls remain responsive. GCM also gives native mobile fold indicators a larger touch target so theme folding offsets do not make heading/list collapse taps unreliable. It tracks already-open Markdown files so switching back to an existing tab preserves the current fold state.
- Right-clicking a Markdown heading or indented list/task parent line with child content adds `Expand all under this line` to the native editor menu. The action opens only visible collapsed folds inside that line's subtree and retries briefly after parent folds open so nested collapsed headings/list items can expand without running note-wide `unfoldAll`.

## Time Tracking And Note Opening

- Time tracking has one start action and infers the tracked object from the surface:
  - Starting from an exact task-line menu, or with the editor cursor on a task, links the session to that task and writes `scheduled` / `timeEstimate` to the task line.
  - Starting from a note/file menu, or with no task under the editor cursor, links the session to that note without creating, changing, or deleting note-level `scheduled`, `timeEstimate`, `end`, `endDate`, or `ends` metadata. Authored note scheduling remains independent from time tracking.
  - Note and process-run targets retain their own canonical metadata. Session state remains in the configured time-tracking record storage, while the editable work-session notes live in the Daily Note workspace.
- Every session has a separate notes workspace in the Daily Note for its start date. The configurable `## Time Tracking` section contains one stable `### time · tracked object` block per work session. The block links back to the task's containing note or the tracked note, and its native block ID lets GCM re-resolve the current notes line after edits above it.
- `Daily Note session placement` defaults to `Top, after properties`; a `Bottom of note` option is also available. A missing section is created at that location. If the heading already exists, GCM preserves its location and adds new sessions first for Top or last for Bottom.
- Session-record storage remains independently configurable as Daily Note, source note, or dedicated note. `notesPath`, `notesHeading`, and `notesBlockId` travel with the record and paused state, so pause/resume and cross-midnight work keep the same notes block. Older records acquire these optional fields only when their notes are opened.
- The notes workspace never becomes the tracked object and never receives timer schedule/duration metadata. Tracking the Daily Note itself also preserves its canonical day-level schedule while creating the session block. Task-linked sessions synchronize only the exact task line; note-linked sessions never schedule either the source note or the Daily Note workspace.
- The desktop status item and mobile timer dock both show the active/paused session. Their primary action opens the editable Daily Note workspace; the context menu keeps **Open tracked item**, pause/resume, and stop.
- `Ignore archived files` is enabled by default. When on, active timer scans skip sessions stored inside the configured archive folder and sessions whose source or resolved target file has moved into that archive folder.
- Time tracking updates its own session state, target metadata, status bar, and affected file UI without opening, pinning, unpinning, or closing editor tabs.
- TPS Home shows a compact timer icon in the header only while GCM time tracking has an active running session. If that active session targets a workout note, Home labels it as a workout for UI purposes, but an active TPS Health workout by itself does not light the timer button.
- TPS Home includes a Workout tracker component that embeds TPS Health's native `Workout Log.base`, creating or repairing that Base through TPS Health when needed. Workout rows remain owned by the Base/TPS Health model rather than a custom Home modal. Stale daily-note workout summaries whose target workout file no longer exists are still cleaned from the Daily Note preview.
- Explicit note opens avoid replacing a pinned tab with a different file and re-resolve the actual opened leaf before focusing/revealing it. This prevents pinned tabs from blocking Notebook Navigator or TPS note-open actions. When a pinned file is the source context, missing target notes open in a new tab; existing target tabs are focused/revealed.
- Normal app-level note opens reuse and focus an existing open tab for the target file. If the target file is not already open, GCM opens it in the requested/current leaf unless that leaf is pinned for a different file; pinned leaves force a new tab. Daily-note prev/next navigation is an explicit same-leaf operation and reuses the current daily-note tab. Background opens, explicit sidebars, and hover previews keep their specialized behavior.
- Home row opens, Home daily-note opens, task API focus, task creation focus, and AI-assisted task creation all route through the same focused-tab opener instead of calling `workspace.getLeaf(false).openFile(...)` directly. This keeps their default behavior consistent: focus an existing target tab, reuse the current unpinned tab, or create/focus a new tab only when the source leaf is pinned, except for hover previews and explicit task context jumps.
- The public GCM API exposes the same focused-tab opener for cooperating plugins. TPS Health uses it for workout/run note starts so workout notes behave like normal time-tracked notes: reuse the current unpinned tab, avoid replacing pinned tabs, and reveal the opened note without forcing a pinned workout tab.
- Notebook Navigator and other native note-open callers remain on Obsidian's native `WorkspaceLeaf.openFile` path. GCM does not globally reroute ordinary markdown opens; the shared focused opener is reserved for GCM-owned calls and cooperating plugin API calls. When a restored tab has markdown state for a file but the editor DOM is blank or has no usable editor body, GCM can reopen that same file during startup/layout repair for plugin-owned focus flows. Inactive pinned empty tabs restored from missing files are left attached during the same repair pass. Same-file duplicates are not automatically collapsed.
- Title sync preserves meaningful previous titles and basenames in `aliases` when GCM changes frontmatter `title`, without replacing existing aliases. Markdown heading typing offers note suggestions from frontmatter title, filename, and aliases; choosing one replaces the typed heading text with a wiki link while preserving the heading level.

## Base Link Preview Preference

- `Force previews for Base links` and the scoped click-preview entry point are exposed through GCM so Calendar, Kanban, TPS List, and TPS Table use the same full-note behavior.
- With `Force previews for Base links` enabled, full-note clicks in Calendar, Kanban, TPS List, and TPS Table open an editable hover-style note card on the first click and the note on a repeated click. TPS uses the third-party Hover Editor when available and its existing responsive local editable preview otherwise, including on mobile. Task-body clicks are kept separate and open the exact-line virtual task editor.

## Status Classification

- GCM owns status normalization and exposes active vs non-active status classification to integrations.
- `Active Status Values` defaults to `todo, working, holding`. Integrations such as TPS Calendar Base should treat configured status options not in that active set as non-active for styling, while recurrence still uses `Completion Triggers`.
- Active status values take precedence for integration classification, so an older recurrence completion setting cannot make an explicitly active status such as `holding` render as completed in Calendar.

## Virtual Base Embeds

- GCM can read note-level frontmatter properties that point at `.base` files and virtually render those Bases inside the note without modifying the note body.
- These are plain frontmatter properties, not GCM custom properties. They can be edited with Obsidian's normal properties UI or other metadata tooling.
- Default keys:
  - `gcmBaseTop`: embeds one or more Bases near the top of the note.
  - `gcmBaseBottom`: embeds one or more Bases near the bottom of the note.
  - `gcmBaseHover`: embeds one or more Bases in a sticky panel that follows scrolling under the note header chrome.
- Values may be a single path/link or a list, for example `[[Related Tasks.base]]`, `Related Tasks`, or YAML list entries.
- The hover placement uses the same mobile suppression behavior as other floating GCM chrome: it hides during swipe collapse or keyboard editing, while normal top/bottom virtual embeds stay in the document flow.
- Virtual Base embeds use Obsidian's normal rendered `![[*.base]]` path. Each referenced Base is rendered as its own virtual item. Top and bottom placements stay unframed and in the note flow so they read like normal embedded note content, while preserving the Base header/toolbar controls needed to switch views, inspect counts, and add records. Empty non-interactive Base items and inline empty-state panes collapse instead of reserving a tall blank pane, but embedded Kanban boards remain visible even when their current result count is zero. GCM mounts into visible reading and Live Preview surfaces, and it remounts if Obsidian replaces the rendered DOM during scroll/layout refresh. It neutralizes TPS Kanban's normal reading-embed vertical transform inside virtual Base hosts so embedded lanes stay in the host instead of jumping behind the note header. Hover placement is the only bounded floating panel and is the only placement where Base chrome is intentionally compacted.
- Canvas nodes containing rendered `.base` embeds are treated as bounded Base panels. GCM keeps Base headers/toolbars visible, hides only generic Markdown embed chrome, and gives table, card, feed, TPS Kanban, TPS List, TPS Health food/workout, and Calendar Base surfaces full-node sizing with internal scrolling. TPS Health food-log Bases use a Canvas-specific compact card layout: source/path text is hidden, entry names wrap, macros stay on their own line, and per-entry action buttons are hidden in narrow canvas nodes so touch-sized controls cannot overlap neighboring cards. These rules are scoped to `.canvas-node-content` and do not depend on TPS Home.
- Current defaults are configured in code through `enableVirtualBaseEmbeds` and `virtualBaseEmbedProperties`; invalid saved entries are normalized back to the three default placements.

The top level is an always-visible five-button hub, and only one destination page renders at a time. Rules and workflows use one additional row of direct buttons instead of nested top-level accordions. The current route and selected editor survive `display()` re-renders as transient UI state and do not add keys to saved plugin settings. A fresh settings-tab instance defaults to **Rules & fields → Frontmatter rules → Sort buckets**.

Disclosures are limited to advanced frontmatter safeguards, one editor per repeated custom field, and the compact Base query reference. Hub buttons expose `aria-pressed`; on narrow screens the hub and secondary selectors become compact horizontal strips, while fixed-width view-mode condition rows stack to one column.
